一个 XOR，把 LDS 读砍掉一半

沐曦 C500 的 int8 MMA kernel 里，取片段那 32 条 LDS 读每条都要 16 拍，而下限是 8 拍。 原因是一行 256 字节正好是 bank 阵列宽度的整数倍，16 条 lane 读 16 个不同的行， 却全部落进同一组 bank。改法是一个异或：槽位 = j ^ (r & 7)， 额外代价 0 字节 LDS。 真机实测 4096³：83.1 → 151.7 TOPS，1.83×。 这页把冲突现场、XOR 为什么管用、以及它不破坏什么，一张图一张图摆出来。

00

先给结论

改动是 LDS 寻址的一行：

// 改之前：行 r 的第 j 个 16B 块，就放在行内第 j 个槽位
#define NOSWZ(r, k)  ((r) * TILE_K + (k))

// 改之后：放在第 (j ^ (r & 7)) 个槽位。j = k >> 4
#define SWZ(r, k)    ((r) * TILE_K + ((((k) >> 4) ^ ((r) & 7)) << 4) + ((k) & 15))
改之前改之后下限
一条 LDS 读指令16 拍8 拍8 拍
一条 LDS 写指令8 拍8 拍8 拍
读用到的 bank 数16 / 3232 / 3232
额外 LDS—0 字节
额外指令—1 条 XOR（地址算式里）
真机 4096³83.1 TOPS151.7 TOPS1.83×

为什么 0 字节很关键：这个 kernel 的 LDS 用量是 2 × 128 × 256 = 65536 字节，正好顶到每 block 64KB 的上限。 教科书上消 bank 冲突的另一招是给每行补齐（行距 256 → 272），它也能修好这个冲突， 但要多 2 × 128 × 16 = 4096 字节 —— 根本放不下。 XOR 是原地重排，一个字节都不多要。

01

bank 的几何：为什么每一行都从 bank 0 开始

LDS 有 32 个 bank，每个 bank 4 字节。一拍里每个 bank 只能吐一个 dword， 所以一拍最多吐 32 × 4 = 128 字节 —— 这就是「一轮」。 地址到 bank 的映射只看地址本身：bank = (字节地址 / 4) % 32，每 128 字节绕回一次。

一条 LDS 访问是 16 字节，占 4 个连续 bank。 一行 TILE_K = 256 字节 = 16 个这样的块 = 整整两轮。

02

冲突现场：谁和谁撞

先打个比方。把 32 个 bank 想成银行的 32 个窗口， 一拍里每个窗口只能办一个人。 一条读指令是 64 条 lane 同时来取数，每人要 4 个 dword，一共 256 个。 要是这 256 个请求均匀摊到 32 个窗口，每个窗口 8 个人，8 拍办完。 要是全挤在 4 个窗口前面，那 4 个窗口每个要办 64 个人 —— 而旁边 28 个窗口在空转。排多少拍，只由最长的那条队决定。

取片段那一步（教程第 05 节的第二段）是这么读的：

const int k_off = q * 16 + c * 64;              // q = lane/16，c = 0..3
af[s][c] = *(const i8x16 *)&As[(wave_m*WM + s*16 + mn) * TILE_K + k_off];
//                                      ↑ mn = lane%16，16 条 lane 读 16 个不同的行
//                                                       ↑ 同一个 q 的 16 条 lane，行内偏移完全相同

光看公式不直观，直接把前几条 lane 的地址算出来。 取 wave_m = 0, s = 0, c = 0，bank = (字节地址 / 4) % 32， 一次读 16 字节 = 4 个连续 dword：

看第 5 列。lane 0‥15 的 dword 号是 0, 64, 128, …, 960 —— 全是 32 的倍数。而 bank = dword % 32， 所以这 16 条 lane 读的虽然是 16 个完全不同的行、完全不同的地址， 算出来的 bank 却一模一样。 行号 mn 对 bank 根本没有发言权，只有 q 说了算。

为什么只碰得到 16 个 bank，而不是 32 个？

上面那张全景图右半边整片空白，这件事值得单独问一句： 64 条 lane 一共要 1024 字节，够铺满 32 个 bank 两圈了， 为什么只落在 16 个 bank 上？

答案是两件事叠在一起，缺一个都不会这么糟：

这一条说了什么单独看的后果
① 指令太窄一条读指令的行内偏移是 q*16 + c*64，q 只有 4 个值 —— 它在一行里只横跨 64 个字节（c 是固定的）。64 字节 = 16 个 dword = 恰好半圈 bank就算只读一行，这条指令也只碰得到 16 个 bank
② 行距太整行距 256 字节是 128 字节的整数倍，每一行都从 bank 0 开始换 16 个不同的行去读，那 64 字节的窗口落在完全相同的 16 个 bank 上

① 决定了只有半圈，② 决定了这半圈叠了 16 层而不是铺开。 把一行的「地图」摊开看最清楚 —— 一行 256 字节 = 16 个槽位， 每个槽位归某一条指令的某一个 q：

所以原始布局下每条读指令的处境都一样：半圈 bank，16 层深。 c=0 堵在 bank 0‥15，c=1 堵在 bank 16‥31，轮流堵，谁也没闲着， 也谁都没快起来。

为什么写不冲突、读才冲突？写的时候分工是 行 = tid/16、行内偏移 = (tid%16) × 16 —— 16 条 lane 铺满同一行的 16 个不同槽位，自然就铺满了 32 个 bank。 读的时候反过来：16 条 lane 落在16 个不同行的同一个槽位。 同一个布局，一个方向顺、另一个方向堵，这是行主序共享内存的典型症状。

03

XOR 怎么修

要让 16 条 lane 散开，就得让同一个逻辑块号 j 在不同的行里落到不同的槽位。 一轮只装得下 8 个块，所以我们只需要 8 种错开方式，取行号的低 3 位 u = r & 7 当偏移量。

用加法（(j + u) % 16）也能错开，但异或更合适：

另外两个实际好处：异或只动块编号的低 3 位，j ^ u 必然还在 0‥15 之内， 不会越到别的行去；而且它作用在块这一层，访问仍然是 16 字节对齐的一整块， 编译器不会把一条 b128 拆成四条 b32。

回到第 02 节那 16 条 lane。q = 0 所以槽位 = 0 ^ (r & 7) = r & 7， lane 几就去第几个槽位：

另外 16 个 bank 是从哪来的？

这是上一节那个问题的另一半。既然一条指令天生只占半圈， XOR 凭什么能让它用上整整 32 个 bank？

答案是跟隔壁那条指令借的。 看 r&7 ≥ 4 的那些行：q ^ u 会把 c=0 的四个块 从槽位 0‥3 推到槽位 4‥7 —— 那原本是 c=1 的地盘，也就是后半圈。 而作为交换，这些行里 c=1 的四个块被推进了槽位 0‥3。 两条指令在这些行上整体对调了半圈：

于是对 c=0 这条指令来说：行号低三位 < 4 的行留在前半圈， ≥ 4 的行跑到后半圈，前后各一半，32 个 bank 全用上。 对 c=1 那条指令正好镜像，也是 32 个。

总量没有变多，只是错开了。 原来 c=0 和 c=1 各自霸着半圈、各自堵 16 层； 现在两条指令都摊到整圈、各 8 层。 bank 总共还是 32 个，数据总量还是 1024 字节， 变的只是「同一拍里的请求有没有撞在一起」。 这也是为什么 XOR 不要额外空间 —— 它没搬走任何东西，只是让两家互换了半边院子。

04

它没破坏写路径

swizzle 最容易出的事故是：读修好了，写塌了。这里没有 —— 写的 16 条 lane 本来就铺满一整行的 16 个槽位，而 XOR 是行内的排列， 排列之后还是那 16 个槽位，只是换了顺序。

全局侧一个字没动。从 A / B 读的地址还是原来的 (block_row + r) * K + koff，合并访问的形状完全没变 —— swizzle 只改「搬进 LDS 之后放哪」，不改「从显存的哪取」。

05

落到代码

mma_swizzle_256.cu 把两种布局做成同一个模板的两个实例， 除了寻址宏以外逐字相同，所以对照是严格的： 

#define LDS_AT(SW, r, k) ((SW) ? SWZ(r, k) : NOSWZ(r, k))

template <bool SW>
__global__ void mma_256(...) {
  ...
  // 第 1 段 写
  *(i8x16 *)&As[LDS_AT(SW, r, ld_k)] = *(const i8x16 *)&A[...];
  ...
  // 第 2 段 读
  af[s][c] = *(const i8x16 *)&As[LDS_AT(SW, ra, k_off)];
}

mma_256<false><<<grid, blk, SMEM_BYTES>>>(...);   // 原始
mma_256<true ><<<grid, blk, SMEM_BYTES>>>(...);   // XOR

SW 是编译期常量，三目运算整个被折掉，XOR 布局里只多出一条真正的 v_xor_b32，而且在循环外就能算好。

文件里还带了一个纯 host 的 bank 模型（./mma_swizzle_256 banks）—— 把 kernel 里那两条寻址宏原样搬到 CPU 上数格子，顺便穷举一遍双射性。 bank 分布是地址的确定性函数，不需要 GPU，也不需要 profiler：

两轮交换了先后顺序，差值在千分之二以内 —— 所以这不是「先跑的那个吃了时钟爬坡」。

1.83× 这个数本身说明了一件事。 这次改动只动了 LDS 读，而读最多只能减半，所以加速比的理论上限就是 2.00× —— 那是「LDS 读占满了全部时间」的极端情况。实测 1.83× 反推回去 （假定其余部分耗时不变、且不与读重叠）， 这 32 条读原本吃掉了总时间的约九成。 换句话说，这个 kernel 之前根本不是算力受限，是被自己的 LDS 读堵死的： 256 条 MMA 一直在等那 32 条读。
