双缓冲的规模分水岭

上一篇的结论是「双缓冲更慢」。这一篇把 TILE_K 切到 128 和 64， 把双缓冲、三级流水一起做出来，在真机上八个组合全部验过数值， 然后发现上一篇那句话只在大矩阵上成立： 4096³ 双缓冲是 0.657×（慢 34%）， 而 1024³ 双缓冲是八个组合里最快的。 分界线不在流水线写得好不好，在block 够不够把这台机器填满 —— 64 个 block 对 104 个 CU，每个 CU 最多也只排得下一个， 这时候双缓冲让掉的那个驻留位子本来就没人坐。

01

先把正确性钉住

八个组合同源实例化（TILE_K × 缓冲数 × 发射方式 × 有无 XOR 四个编译期开关）， 真机逐个对 CPU 参考：

  TK=128 单缓冲晚发射   PASS  (0/65536 不符)
  TK=128 双缓冲         PASS  (0/65536 不符)

这件事值得单独说一句：流水线的错不会让结果偏一点，会让它错得很明显 —— 读到还没落地的数据，或者盖掉别人还没读完的缓冲，出来的就是垃圾。 所以「0/1048576 不符」同时也是时序正确的证据。

02

切 K 是为了把缓冲做小，不是为了把窗口做多

TILE_K=256 时一份缓冲就是 2 × 128 × 256 = 65536 B， 正好顶满每 block 的上限，双缓冲根本放不下。所以要先切 K： 

TILE_K = 256：一份 64 KB    两份 128 KB  // 放不下
TILE_K = 128：一份 32 KB    两份  64 KB  // 正好用满 ← 本篇重点
TILE_K =  64：一份 16 KB    两份  32 KB  // 还剩一半

切 K 不改变总工作量：窗口数翻倍、每窗的 LDS 读和 MMA 各减半， 读:MMA 恒为 1:8。它改变的是三件别的事 —— LDS 占用、barrier 条数、 以及全局侧每行的连续段长（TILE_K 就是段长）。

03

双缓冲长什么样

一块地在算，另一块地在搬，每轮换手：

load_win(buf 0, 窗口 0);              // 预热
for (tk = 0; tk < nwin; ++tk) {
    arrive_gvmcnt(0);                 // 等本窗落地
    barrier;                          // 过了这里，上一轮读的那块地就没人要了
    load_win(另一块, 窗口 tk+1);       // ← 读之前就能发，写的是另一块地
    读 buf[cur] -> 寄存器
    128 条 MMA                        // 搬运在这段时间里飞
}

所以双缓冲在流水线这件事上确实做得更好。 它输掉的从来不是重叠，是那第二份 LDS 顶掉的驻留位子。 下一节说明这笔账什么时候划得来。

04

分水岭：block 够不够把机器填满

为什么规模能决定名次？因为「每 CU 驻留两个 block」这件事 只有在 block 排队的时候才有价值。这张卡有 104 个 CU， 而一个 block 算 128×128 的 C：

一句话的判据。 (M/128) × (N/128) 明显小于 CU 数 → 用双缓冲； 明显大于 → 用单缓冲晚发射，把 LDS 省下来换驻留。 这条线和 K 无关：K 只决定窗口数，不决定 block 数。

05

再切一刀到 TK=64：驻留 4 个 block，照样亏

TK=64 看起来是两头都要的那个点：两份缓冲只占 32KB， 驻留和块内重叠同时拿到；而且顺带把 bank 冲突也消了（第 06 节）。 单缓冲更是能驻留到 4 个 block/CU。实测全部打脸：

组合LDS驻留4096³ TOPS段长/行
TK=128 单缓冲晚发射32 KB2292.2128 B
TK=64 单缓冲晚发射16 KB488.764 B
TK=64 双缓冲32 KB2155.464 B
TK=64 三级流水48 KB1142.564 B

驻留翻到 4 个，TOPS 反而从 292.2 掉到 88.7。 原因在最后一列：一行在一个窗口里只取 TILE_K 个字节， 所以 TILE_K 就是全局侧的连续段长。 本机早先实测过跨距读对段长极其敏感（跨距 8KB）： 段长 64 B 只有 324 GB/s（线性峰值的 20%），512 B 有 1234 GB/s（77%）。 切 K 赚驻留、亏 DRAM 效率，256→128 那一刀赚，再往下这一刀亏。

一个反直觉的细节。在 TK=64 这档里， 驻留 4 个 block 的单缓冲（88.7）反而比驻留 2 个的双缓冲 （155.4）慢 1.75×。 段长只有 64 B 的时候，访存请求又小又多，4 个 block × 256 线程一起发会把访存通路打满； 这时候「少一点并发、深一点预取」反而更好。 所以驻留度不是越高越好，它和每个请求的大小是一对的。

06

顺带：为什么 TK=128 还得留着 XOR，TK=64 就不用了

bank 冲突的根子是「行距是 128 B 的整数倍，于是每行都从 bank 0 开始」。 切 K 会改行距，所以切完要重新算一遍：

XOR 在双缓冲下比在上一篇更值钱：4096³ 去掉它要赔 2.30×，而上一篇 TK=256 单缓冲下只有 1.85×。 解释是同向的 —— 驻留只剩一个 block 时，没有别的 block 来帮着盖 LDS 冲突的延迟。 （这是推论，没有 profiler 直接证据。）

07

三级流水，和一个只在 host 上才抓到的错

TK=64 下还放得进第三块缓冲（48KB）。多级流水要的不是 gvmcnt(0) 而是部分等待：等最老那个窗口落地， 让更晚的继续飞。写出来是这样： 

constexpr int WAITC = (NBUF - 2) * OPS;   // 允许 NBUF-2 个窗口还在飞
arrive_gvmcnt(WAITC);

这段是错的。没有真机的时候，用 host 逐步模拟主循环，穷举 nwin=1..40：

A. gvmcnt 固定允许 NBUF-2 个在飞
   NBUF=2 双缓冲    全部通过
   NBUF=3 三级流水  40 个 nwin 全错 -> 读窗口 0 时它还在飞
B. 排空阶段降回 gvmcnt(0)
   全部通过

双缓冲不受这个影响：NBUF=2 时 WAITC 本来就是 0， 等的就是 gvmcnt(0)。所以这个坑只在往更深的流水走的时候才踩到。 修好之后三级流水在真机上 256³ / 1024³ 都 PASS， 也就顺带验证了 gvmcnt 是按发射序回落的 —— 这件事之前没有依据，只能靠正确性检查来裁决。

性能上三级流水没意义：48KB 把驻留压回 1 个 block， 4096³ 只有 142.5 TOPS，比同 TK 的双缓冲还慢。
