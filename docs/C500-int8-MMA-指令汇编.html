MMA 的四个操作数

上一篇把异步搬运那条指令扒到了汇编，这一篇轮到 __builtin_mxc_mma_16x16x16i8。 汇编里它就是一条 mma_16x16x16i8 rD, rA, rB, rC —— rD 和 rC 被编译器合成同一组寄存器（原地累加）， 而那组寄存器就是四个普普通通的向量寄存器， 能清零、能从内存 load、能四个并存互不相干。 教程第一篇靠推理得出的「acc 是线程私有的」，现在有了指令级的证据。 顺带还查清了两件事：依赖链上的 MMA 背靠背发射、中间零等待， 以及 K=32 那条指令真实的操作数类型 —— 我之前猜错了。

00

结论速查

问题汇编给的答案
指令形态mma_16x16x16i8 r4, r2, r1, r4 —— 目的、A、B、累加输入
acc 住在哪4 个连续的普通向量寄存器（i32x4），线程私有，没有任何专用通道
怎么累加编译器把 rD 和 rC 合成同一组 —— 原地累加，零拷贝
A / B 片段各一个 32 位向量寄存器（4 个 int8 打包），取数就是一条 ldg_b32
依赖链要不要等不要。四条累到同一个 acc 的 MMA 在汇编里紧挨着，中间无任何等待指令
什么时候要等MMA 之后接普通指令读 acc 时要垫 snop：K=16 是 snop 3，K=32 是 snop 5
K=32 的助记符mma_i32_16x16x32i8（多了 i32 中缀），片段 8 B，取数是 ldg_b64

01

一条指令，四个操作数

最小的探针：读两个片段，乘加一次，写回。整个 kernel 的有效部分就四行：

ldg_b32  r2, s0, r1, 0x0      // A 片段：一个 32 位寄存器
ldg_b32  r1, s2, r1, 0x0      // B 片段
arrive   gvmcnt(0)
mma_16x16x16i8 r4, r2, r1, r4 // ← 就这一条
snop 3
stg_b128 s4, r0, 0x0, r4 devc

02

acc 就是四个普通寄存器

教程第一篇讲过「acc 是线程私有的寄存器，指令是 wave 级的集体操作」， 但那是从片段映射推出来的。现在可以直接验：把累加器换四种用法，看汇编认不认。

这也解释了累加器为什么这么贵。 一个 16×16 的输出块要 4 个寄存器， mma_dbuf_256.cu 里每个 wave 扛 4×4 个输出块 —— 就是 64 个向量寄存器只用来放累加器。 前一篇的占用率那张表里，寄存器压力就是这么来的。

03

依赖链背靠背，只有链尾要等

四条 MMA 全累到同一个 acc，每一条都依赖上一条的结果。 直觉上这应该是最糟的情形，但汇编里它们紧挨着： 

mma_16x16x16i8 r10, r2, r6, r10
mma_16x16x16i8 r10, r3, r7, r10
mma_16x16x16i8 r10, r4, r8, r10
mma_16x16x16i8 r10, r5, r9, r10
snop 3                            // ← 只有这里垫了
stg_b128 s4, r0, 0x0, r10 devc

06

两条路径各测到了哪一步

同一份源码，-DMX_ARCH=500 走 K=16、-DMX_ARCH=600 走 K=32。 两边都测，但能测到的深度不一样：

两边的 host 自检输出逐字相同（这正是应该的 —— 布局和 k 覆盖跟 MMA 的 K 无关）：

=== 自检 ===
  原始 写进去的块 <-> 读出来的块：全部对上
  XOR  写进去的块 <-> 读出来的块：全部对上
  原始 全局侧一行内的足迹：仍是那一段连续字节，只换了取数的人
  XOR  全局侧一行内的足迹：仍是那一段连续字节，只换了取数的人
  (c, w) 两层循环铺出的 256 个 k：不重不漏

所以 K=32 的状态要说准确： 签名已核实、整份文件编得过、指令形态和条数都对、下标算术自检全过 —— 但片段的 lane→元素映射和累加器布局仍然是推的。 这两件事只有真卡能判，banks 验不到。

07

mma_i32_16x16x32i8 r18, r12, r16, r18
