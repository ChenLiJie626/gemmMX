一条 MMA 指令，从 16B 搬运到输出

沐曦 C500 的 __builtin_mxc_mma_16x16x16i8：C = A(256×256) × BT， 每个线程搬 16 字节。分工与 kernel_test_v1.cu 一致 —— 只讲数据排在哪、哪个 block / wave 负责哪块、结果从哪来。

01

这条指令算什么

typedef __attribute__((ext_vector_type(4))) int i32x4;

acc = __builtin_mxc_mma_16x16x16i8(a, b, acc);
//                                 ↑  ↑   ↑
//                           int   int   i32x4

一条指令完成 C(16×16) += A(16×16) × B(16×16)，由 一个 wave 的 64 条 lane 协作完成。 注意三个参数的类型：

  • a、b 是 int，不是指针也不是向量 —— 4 个 int8 打包进一个 32 位寄存器。这是 SDK 里 __frag_base<signed char, 4, 1> 的 storage 就是 1 个 int 的缘故。
  • acc 是 4 个 int32。

所以每条 lane 只提供 4 个 A 元素 + 4 个 B 元素，拿回 4 个 int32。 64 lane × 4 = 256 = 16×16，刚好铺满 A、B、C 三个矩阵。

本卡是 xcore1000。SDK 里那条更宽的 mma_16x16x32i8 在 #if __MACA_ARCH__ == 1500 分支里，这张卡用不了， 能用的只有 K=16 这条。

02 — 数据排布

a、b 寄存器里到底装了什么

先把规模缩到一条指令看：A 是 16×16 字节、B 是 16×16 字节，各 256 字节。 一个 wave 64 条 lane，64 × 4 = 256 —— 每条 lane 恰好分到 A 的 4 个字节、B 的 4 个字节，不重不漏。

每条 lane 拆成两个号码，后面几张图都用它：

p = lane % 16     // 0..15  决定「第几行 / 第几列」
q = lane / 16     // 0..3   决定 k 的窗口,k = 4q..4q+3

图 1  a 寄存器 = A 里横着躺的 1×4

A 是行主序 A[m][k]。lane 拿到的是第 p 行、从 k=4q 起连续 4 个。 每个格子就是一条 lane 的 a 寄存器，格内 3 条淡线表示它是并排的 4 个字节。

图 2  b 寄存器 = B 里竖着站的 4×1

数学上的 B 是 B[k][n]，k 在竖轴。lane 拿到的是第 p 列、从 k=4q 起连续 4 个 —— 同一个 lane = 16q + p 公式，只是 p 这次是列号 n，不是行号 m。 格内 3 条淡线表示它是上下叠起来的 4 个字节。

图 1 和图 2 是同一件事。 a 装的是「A 里沿 k 走 4 步」，b 装的也是「B 里沿 k 走 4 步」。 区别只在自由下标 p：在 A 里它是行号 m，在 B 里它是列号 n。 所以一个看起来是横条、一个看起来是竖条 —— 但两者都沿着 k。

图 3  寄存器里 4 个字节的顺序

两个寄存器都是一样的规矩：从低字节到高字节，永远是 k 递增。

一个常见误解：我手上的 a × 我手上的 b ≠ 我手上的 C。 lane 17 只有 A 的 4 字节和 B 的 4 字节，凑不出任何一个 C 元素。 硬件在 wave 内部把 64 份 a 和 64 份 b 交叉相乘，谁配谁不用你管 —— 你只要保证自己那 4 个字节放在对的位置。顺便，lane 17 的累加器里装的是 C[4][1], C[5][1], C[6][1], C[7][1]，和它自己的 a、b 都没关系。

图 4  同一批 64 人，三张座位表

上面那条「谁配谁不用你管」，其实有一张明明白白的表。先说为什么非得协作： 一条 MMA 要算的是 C[m][n] += Σ(k=0..15) A[m][k]·B[k][n]， 这个和式要 16 个 k 全凑齐才有意义； 可一条 lane 的寄存器只有 32 位 = 4 个 int8，装不下 16 个 k。 所以 k 必须切成 4 段分给 4 条 lane —— 一个输出格子的原料，天生就散在好几条 lane 手里。

p = lane%16 和 q = lane/16 这两个号，在三件事里扮演的角色不一样：

两条好记的结论。 列对得上：②和③里 p 都是列号， 所以一条 lane 交的那一列 B，正是它最后领走的那一列 C。 行对不上：①里 p 是行号，③里行号却变成了 4q + e —— B 那边自给自足，A 那边必须靠别人。

图 5  一个格子，到底是谁和谁凑出来的

拿 tile 里的 C[5][3] 走一遍，三张表轮流查： 

要算 C[5][3] = Σ(k=0..15) A[5][k] · B[k][3]

A 的第 5 行，散在 4 条 lane 手里（查表①，p=5 那一行）
   lane  5 -> k  0‥3      lane 21 -> k  4‥7
   lane 37 -> k  8‥11     lane 53 -> k 12‥15

B 的第 3 列，散在另外 4 条 lane 手里（查表②，列 3 那一竖）
   lane  3 -> k  0‥3      lane 19 -> k  4‥7
   lane 35 -> k  8‥11     lane 51 -> k 12‥15

8 条 lane 的料凑成这一个数。结果发给谁？（查表③）
   行 5 落在「行 4‥7」那组 -> q=1；列 3 -> p=3
   -> lane 19，放在它的 e = 5%4 = 1 那一格

硬件凭什么能跨 lane 取数？ 普通指令里 lane 之间是隔离的 —— v_add 只能加本 lane 的东西， 想跨 lane 求和得专门发 shuffle / DPP。但物理上，一个 wave 的 64 条 lane 的同一个寄存器号 本来就是一整块连续的 VGPR，硬件一次能全读出来。 MMA 做的事，就是把「跨 lane 的那次归约」直接做进了矩阵单元里： 你交寄存器，它在内部拼 k、乘、加、规约，再按表③派发。 不经过 LDS，不发 shuffle，不占你一条指令。

顺便算笔账，看它为什么划算。 一条 MMA 的输入总共才 256 + 256 = 512 字节（64 人各 8 字节）， 却要做 4096 次乘加。差的 8 倍来自复用： A[m][k] 这一个字节要参与 C[m][0..15] 全部 16 个输出， B[k][n] 要参与 C[0..15][n] 全部 16 个输出。 硬件在阵列内部把每个片段广播给 16 路，寄存器只读一遍 —— 这就是 MMA 比手写点积快的全部理由。

图 6  那根竖条在内存里是竖的还是横的？

前面那几张图跟 B 怎么存完全无关 —— 寄存器内容是硬件定死的。 存法只决定一件事：凑出那 4 个字节要花几条指令。 下面把 lane 17 的 4 个 B 字节在内存里标出来（取 K=N=16，格子按行主序铺， 地址 = 行×16 + 列）：

右边那种存法下，A 和 B 的地址算式变成了同一条： 

a 的 4 字节: &A[p * K + 4q]      // 偏移 1*16+4 = 20,21,22,23
b 的 4 字节: &B[p * K + 4q]      // 偏移 1*16+4 = 20,21,22,23  ← 一模一样

这就是后面「A 和 B 形状同构、同一套搬运代码跑两遍」的全部含义。

所以 row_major / col_major 不是「快 / 慢」。 规矩是：谁把 k 放在最快变化的那根轴上，谁就只要一条读。 A 的 k 在列方向 → A 要 row_major；B 的 k 在行方向 → B 要 col_major。 两个词不一样，说的是同一件事 —— 让 k 连续。

03

两个矩阵都是 [行][K]，所以不用转置

教学 kernel 的数据约定（和 kernel_test_v1.cu 一致）： 

A:  M × K  行主序 int8      // A[m][k]
B:  N × K  行主序 int8      // B[n][k]  ← 已经是转置形态
C:  M × N  行主序 int32

B 存成 [n][k] 而不是 [k][n]，这一个决定省掉了全部转置代价 —— 上一节的图 6 就是这件事的图解。SDK 里对应的是两个 B 加载版本： 

// matrix_b / col_major —— 一条 4B 读
f.x[0] = *(int *)(p + col * ldm + row);

// matrix_b / row_major —— 4 条单字节读 + union 拼
tmp.c[0] = p[row * ldm + col];
tmp.c[1] = p[(row + 1) * ldm + col];  // ... 共 4 条

col_major 的 B 就是 BT 行主序，即 [n][k]。 既然 host 侧已经是这个形态，A 和 B 的 LDS 布局与搬运代码完全同构 —— 同一套下标，跑两遍。

04 — 区域划分

哪个 block、哪个 wave 负责哪块

前三节只看一条指令。现在把规模放到 M=N=K=256， 分工照搬 kernel_test_v1.cu：block tile 128×128×256、 一个 block 256 线程 = 4 个 wave、wave 排成 2×2。

于是从 C 的一格往上追，正好四层。每一层都只是在上一层里再切一刀：

层有几个每个管多大由谁决定
block2×2 = 4128 × 128 blockIdx.y / blockIdx.x
wave2×2 = 464 × 64 wave = tid/64，wave_m = wave/2，wave_n = wave%2
MMA tile4×4 = 1616 × 16 循环下标 mm / nn
lane644 个 int32 lane%16 定列，lane/16 定行组

乘起来对账：4 block × 4 wave × 16 tile × 256 元素 = 65536 = 256×256。

权威定义就是写回那四行

与其背公式，不如直接看 kernel 最后怎么写 C —— 四层偏移一层层加上去，顺序一眼可见： 

const int row = block_row + wave_m * 64 + mm * 16 + (lane / 16) * 4;
const int col = block_col + wave_n * 64 + nn * 16 + (lane % 16);
for (int e = 0; e < 4; ++e)
  C[(row + e) * N + col] = acc[mm][nn][e];
//    ↑block     ↑wave      ↑tile     ↑lane  ↑片段分量

把它反过来就能从任意 C[m][n] 反推出主人，下一节的点选图用的就是这个： 

by = m / 128;  bx = n / 128;              // 哪个 block
wave_m = (m % 128) / 64;  wave_n = (n % 128) / 64;
mm = (m % 64) / 16;  nn = (n % 64) / 16;  // wave 内哪个 tile
lane = ((m % 16) / 4) * 16 + (n % 16);
e    =  (m % 16) % 4;

注意两处容易混的地方。 一是 wave_m = wave/2 走 M、wave_n = wave%2 走 N， 所以 wave 0/1 是上面一排、wave 2/3 是下面一排； 二是 mm/nn 的步长是 16 而不是 64 —— 一个 wave 的 4×4 个 tile 在它那 64×64 里是紧挨着铺满的，不是跳着放。

算完之后怎么归位

没有「归位」这一步。256 条 MMA 跑完，那 64 个 int32 从头到尾待在寄存器里没动过 —— 不汇总、不经 LDS、不跨 lane 搬运。每条 lane 自己算出自己那几个数在大矩阵里的全局地址，直接 store， 64 条 lane 同时发。所谓「映射」，就是把四个基址加起来。

四段偏移的来源各不相同，但都是编译期常量或者一两条移位（128、64、16、4 全是 2 的幂）：

层行偏移列偏移谁决定
blockblockIdx.y * 128blockIdx.x * 128启动配置
wavewave_m * 64wave_n * 64tid / 64 拆成 2×2
tilemm * 16nn * 16两重循环下标
lane(lane/16)*4 + elane % 16硬件定死

前三层是我们自己摆的，想换分工改掉就是；最后一层动不了 —— acc 的布局是 MMA 指令的一部分。整套映射没有查表、没有通信、没有除法， 运行时代价基本为零。

为什么不会撞车、也不会漏。 一个 wave：16 个 tile × 64 条 lane × 4 个 e = 4096 = 64×64， 正好铺满它那块，一个不多一个不少；4 个 wave 拼成 128×128，4 个 block 拼成整个 C。 这不是推演 —— 真机上用 prov_256 探针把 65536 个元素逐个 dump 出来和公式对账， 0 处不符、0 个未覆盖、0 个重复。

一条 lane 要写几次？64 次

写回阶段每条 lane 发 64 条 store，每条 4 字节，共 256 字节。 账很好算：16 个 acc × 每个 4 个 int32 = 64。 这 64 个数不是挨着的，而是按一个很规整的格子散在 wave 那块 64×64 上：

粒度次数每次合计
一个 acc44 B16 B
一条 lane644 B256 B
一个 wave64 条指令64 lane × 4 B16 KB
一个 block—4 个 wave64 KB

注意第三行：「64 次」是指令条数，不是访存次数。 一条 store 指令是整个 wave 一起发的，64 条 lane 各写 4 字节 —— 其中每 16 条 lane 的列号连号，凑成 16 个 int32 = 64 字节一段， 一条指令产生四段 64 字节（四组 lane 的行号差 4）。 所以从内存看，这 64 条指令一共搬 64 × 256 B = 16 KB，正好是 64×64×4。

这 64 次之间没有依赖，顺序随便排，编译器可以拿它们盖住尾部的延迟。 但单个 4 字节 store 的效率确实不如宽写 —— 想凑出 16B 甚至 128B 的宽写，就得先把 acc 过一遍 LDS 重排， 用一次额外的来回换更少的访存指令。这个教学 kernel 没做， 规模大的时候写回只占总时间的很小一块（64×64 的输出摊在 K 那么长的计算上）。

写回时的访存形态值得留意：固定 (mm, nn, e) 的那一条 store， 64 条 lane 写的是四段各 64 字节（每 16 条 lane 的列号连号，凑成 16 个 int32）， 而一条 lane 自己的 4 个数反倒隔着 N×4 字节。 合并发生在 lane 之间，不在 lane 内部 —— 第 05 节末尾有图。

两个容易栽的坑。 一是 dim3 grid(N/128, M/128) —— x 管列、y 管行， block_row 取的是 blockIdx.y。写反了不报错，方阵时尤其阴险。 二是这个教学 kernel 不做边界判断：M、N 必须是 128 的整数倍，K 必须是 256 的整数倍， 否则直接写飞。真要上生产，搬运和写回两处都得加 predicate （kernel_test_v1.cu 用的 __builtin_mxc_ldg_b128_bsm_predicator 就是干这个的）。

05

16 字节走完三段路

一个 block 要把 A 的 128×256 和 B 的 128×256 搬进 LDS， 共 64 KB（整块 LDS 都用上了，所以一个 CU 只驻留一个 block）。

第一段：global → LDS，16 个线程合搬一行

一行是 TILE_K = 256 字节，16 个线程 × 16B 正好等于 256B。 block 有 256 个线程，所以一轮搬 16 行，128 行要 8 轮。 A 和 B 的下标算式一模一样 —— 因为 B 在 host 侧就是 [n][k]。 

const int ld_row = tid / 16;        // 0..15  本轮搬第几行
const int ld_k   = (tid % 16) * 16;  // 0..240 该行第几个 16B

#pragma unroll
for (int i = 0; i < 8; ++i) {          // 8 轮铺满 128 行
  const int r = ld_row + i * 16;      // 0..127
  *(i8x16 *)&As[r * 256 + ld_k] = *(const i8x16 *)&A[(block_row + r) * K + ld_k];
  *(i8x16 *)&Bs[r * 256 + ld_k] = *(const i8x16 *)&B[(block_col + r) * K + ld_k];
}

相邻的 tid 读相邻的 16B，16 个线程合起来是 256B 连续，访存可以合并。 LDS 里的布局和 global 完全相同，不重排。

第二段：LDS → 寄存器，一次 16B 读 = 4 个片段

这是整段路里最密的一步。拆成三个问题看就清楚了：读哪儿、 读回来是什么、读回来喂给谁。 

const int mn = lane % 16;   // tile 内:A 的行 / B 的列
const int q  = lane / 16;   // 0..3  k 组内的第几个 16B

i8x16 af[4][4], bf[4][4];               // [s][c],每个含 4 个片段
#pragma unroll
for (int s = 0; s < 4; ++s)             // wave 内第几个 16 行
#pragma unroll
  for (int c = 0; c < 4; ++c) {           // 第几个 k 组
    const int k_off = q * 16 + c * 64;
    af[s][c] = *(const i8x16 *)&As[(wave_m * 64 + s * 16 + mn) * 256 + k_off];
    bf[s][c] = *(const i8x16 *)&Bs[(wave_n * 64 + s * 16 + mn) * 256 + k_off];
  }

循环体执行 4 × 4 = 16 次，A、B 各一条读 —— 一共 32 条 16B 读，换来 64+64 个片段。

问题二：读回来是什么

16 字节 = 4 个 int，而每一个 int 就是一个完整的 MMA 片段（4 个 int8 打包进 1 个 32 位寄存器，低字节对应小 k）。 所以一条读指令喂 4 条 MMA：

为什么偏移是 q*16 而不是 q*4？ 硬件要的是每条 lane 在一条指令的 16 宽窗口里提供 k0 = 4q。 但这里让 4 个 lane 组各取一整个 16B：q=0..3 分别拿走 64c+0、+16、+32、+48 —— 合起来正好铺满这个 k 组的 64 字节，一个字节不漏不重。 代价是送进每条 MMA 的 k 顺序被打乱了，而这不要紧 —— 下面第 08 节讲为什么。

问题三：读回来喂给谁

这 32 条读要支撑 256 条 MMA，靠的是复用： 累加器排成 4×4，acc[m][n] 吃的是 af[m][c][w] × bf[n][c][w] —— m 只挑 A、n 只挑 B，所以同一个 A 片段对 4 个不同的 n 各用一次。

对一遍账（每个 wave、每个 k 窗口）：

次数字节
LDS 实际读32 条 × 16B512 B
MMA 逻辑消耗256 条 × (4B + 4B)2048 B
复用倍数—4×

如果不做寄存器分块（一个 wave 只算一个 16×16 tile），256 条 MMA 就要 512 条读 —— 整整 16 倍。LDS 带宽会立刻变成瓶颈。

最后一个容易绕进去的点。 lane 17 读的是 As 行 1/17/33/49，也就是 A[129]、A[145]、 A[161]、A[177]；但它拥有的是 C[164..167][81]（第 07 节那个例子）。 供 A[164] 的是 mn = 164%16 = 4 的那批 —— lane 4 / 20 / 36 / 52，跟它不是同一条。 再强调一次：片段在 MMA 单元内部跨 lane 流动，你读的和你拥有的没有对应关系。

第三段：256 条 MMA，和累加器里那 4 个数

四重循环：4(m) × 4(n) × 4(k 组) × 4(word)。K=256 一个窗口就吃完了， 所以外层的 k 循环只走一轮。 

for (int m = 0; m < 4; ++m)
  for (int n = 0; n < 4; ++n)
    for (int c = 0; c < 4; ++c)
      for (int w = 0; w < 4; ++w)
        acc[m][n] = __builtin_mxc_mma_16x16x16i8(af[m][c][w], bf[n][c][w], acc[m][n]);

每个 wave 256 条，全局 4 block × 4 wave × 256 = 4096 条 —— 正好等于 (256/16)³。下面把这 256 条拆开看三件事。

问题一：一条 MMA 里，这条 lane 到底算了什么

先把最容易想歪的地方说清楚：它谁也没单独算。 MMA 是整个 wave 一条指令，不是 64 份小活。64 条 lane 把各自的 4 个 A 字节和 4 个 B 字节交上去，硬件把完整的 16×16×16 = 4096 次乘加做完， 再按一张固定的表把 256 个结果发回 64 条 lane。 交进去的归属和拿回来的归属，是两张不同的表。

对照 SDK 的三个取数公式，一眼能看出哪边对得上：

行 / k列
a 片段行 = lane%16k = 4·(lane/16) + 0‥3
b 片段k = 4·(lane/16) + 0‥3列 = lane%16
acc行 = (lane/16)·4 + e列 = lane%16

列对得上：b 片段的列和 acc 的列都是 lane%16 —— 一条 lane 交的那一列 B，正是它最后持有的那一列 C。 行对不上：a 片段的行是 lane%16，acc 的行却是 (lane/16)·4 + e。 所以 B 那边自给自足，A 那边必须靠别人。

拿真数据走一遍。block (0,1) / wave 1 / lane 17 的第一条 MMA（m=2, n=1, c=0, w=0）：

它交出去的两个片段（k = 16‥19，因为 q = lane/16 = 1）
  a = A[161][16..19] = [ 2,  4, -1,  6]     // 行 161 = tile 基 160 + lane%16
  b = B[ 81][16..19] = [ 7,  2,  5,  2]     // 行  81 = 列基  80 + lane%16

这两个片段自己的点积 = 2·7 + 4·2 + (-1)·5 + 6·2 = 29
  -> 落在 C[161][81]，归 lane 1 的 acc[2][1][1]，不归 lane 17

lane 17 自己的 acc[2][1][0] 要的是 A[164] 那一行
  -> 164 在 tile 内是第 4 行 -> 由 lane%16 == 4 的那批交上来
  -> lane 4 / 20 / 36 / 52（四条各管 16 个 k）

一句话记住：lane 是「交数据的单位」和「存结果的单位」，但不是「算一个数的单位」。 算是 wave 整体在算。想问「lane 17 算的是哪个位置」， 准确的问法是「lane 17 持有的是哪个位置」 —— 那才有确定答案。

问题二：16 条 MMA 怎么累成一个数

固定一对 (m, n)，剩下的 c、w 两重循环是 16 条 MMA，全部打在同一个 acc[m][n] 上。 每条带来 16 个 k 的贡献，16 × 16 = 256，正好是一个 K 窗口。 累加的位置自始至终是同一组寄存器 —— 不落 LDS，不落显存， 读出来、加上去、写回去，全在寄存器里。

注意每条 MMA 覆盖的 k 不是连续的 16 个，而是四段 4 连号 （q=0..3 四组 lane 各贡献一段）。这就是第 08 节那个 k 置换 —— 加法不在乎顺序，所以它无害。

K 比 256 大的时候，外层 tk 循环接着跑，累加器不清零： K=4096 时每个 acc[m][n] 要吃 16 × 16 = 256 条 MMA， 整整 256 条串行依赖打在同一组寄存器上。 这也解释了为什么要摆 4×4 个累加器而不是一个： 16 条独立的依赖链交错发射，才填得住 MMA 的延迟。

问题三：这 4 个数最后写到哪

256 条 MMA 跑完，16 个 acc[m][n] 一共 64 个 int32 还躺在寄存器里。 写回就是把 e=0..3 展开成四行： 

row = block_row + wave_m*64 + m*16 + (lane/16)*4;
col = block_col + wave_n*64 + n*16 + (lane%16);
C[(row + e)*N + col] = acc[m][n][e];        // e = 0..3

lane 17, m=2, n=1:  row = 128 + 0 + 32 + 4 = 164,  col = 0 + 64 + 16 + 1 = 81
  acc[2][1][0] -> C[164][81] = -234
  acc[2][1][1] -> C[165][81]
  acc[2][1][2] -> C[166][81]
  acc[2][1][3] -> C[167][81]

三段路到这儿接上了。 16B 从显存进 LDS（第一段）→ 一条 16B 读拆成 4 个片段进寄存器（第二段）→ 256 条 MMA 把它们碾成 64 个 int32（第三段）→ 4×16 次 store 回显存。 全程一条 lane 读的、算的、持有的是三组不同的坐标， 唯一真正属于它的，是最后那 64 个 int32 的位置。

对照 kernel_test_v1.cu：为什么看起来次数不一样

把两份代码的第三段摆一起，循环嵌套一个是 4 层、一个是 3 层，很容易以为算的条数不同。 其实一样，都是 256 条 —— 差别只在最内那层写不写成循环。

本页的写法：四层循环，最内层是 word。

for (m < 4) for (n < 4) for (c < 4) for (w < 4)
    acc[m][n] = mma(af[m][c][w], bf[n][c][w], acc[m][n]);

// 4 × 4 × 4 × 4 = 256

kernel_test_v1.cu 的写法：三层循环，word 那层被手工展开进宏里。

// 一次宏 = 两条 MMA（相邻两个 word）
#define MMA_MNK_I(mm, nn, kk, ii)                                      \
    acc[mm][nn] = mma(a[mm][kk][(ii)*2],   b[nn][kk][(ii)*2],   acc[mm][nn]); \
    acc[mm][nn] = mma(a[mm][kk][(ii)*2+1], b[nn][kk][(ii)*2+1], acc[mm][nn]);

for (m < MMA_M) for (n < MMA_N) for (k < kLdsNumPerK) {
    MMA_MNK_I(m, n, k, 0);     // word 0、1
    MMA_MNK_I(m, n, k, 1);     // word 2、3
}

// 4 × 4 × 4 × (2 + 2) = 256

看得见的循环只有 3 层，但循环体里躺着 4 条 MMA。乘回去还是 256。 往上一层也一样：每个 wave 每个 k 窗口 256 条，全局 (M/16)·(N/16)·(K/16) 条，两份代码分毫不差。

这一层是什么本页 mma_teach_256.cukernel_test_v1.cu
片段数组i8x16 af[4][4]ABType a[kStage][kLdsNumPerK][4]
M 方向第几个 16 行for m < 4for m < MMA_M (=4)

名字别被带偏。kernel_test_v1.cu 里那几个常量名不是字面意思： kStage 不是流水级数，它是「M 方向第几个 16 行」（本页叫 s/m）； kLdsNumPerK 是「第几个 k 组」（本页叫 c）； 最后那维 [4] 才是「一次 16B 读里的第几个 word」（本页叫 w）。 认准这三个，两份代码就能逐行对上。

还有一个命名陷阱，在本页这份代码里。 typedef __attribute__((ext_vector_type(4))) int i8x16; —— 名字写着 16 个 int8，实际是 4 个 int（合起来确实是 16 字节）。 所以 af[m][c][w] 里的 w=0..3 取的是第 w 个 4 字节片段， 不是第 w 个字节。kernel_test_v1.cu 那边 ABType = int32_t、 a[..][..][4] 直接就是 4 个 int，没有这个歧义。

v1 为什么要手工展开？两条连写等于把「同一个 acc、相邻两个 word」的发射顺序钉死， 不依赖 #pragma unroll 的行为；宏的 ii 参数也留了插空位置 （要插预取或 fence，就插在两次宏调用之间）。本页写成四层循环加 #pragma unroll， 图的是让 4×4×4×4 这个结构一眼可见 —— 教学优先。

这里只谈源码形态，不下性能结论。 两种写法都会被全展开成 256 条，编译结果大概率几乎一样， 但我没在真机上比过两者的汇编和耗时，所以不说哪个快。

06 — 交互查询

哪条 lane 持有哪个元素

三个矩阵的 lane→元素映射，全部摘自 SDK load_matrix_sync 原文。 点一个 lane，看它在 A / B / C 里分别碰到哪些格子。

A · matrix_a row_major
行 = lane & 15
列(k) = (lane >> 4) × 4，共 4 个
k=0k →15
B · matrix_b col_major
列(n) = lane & 15
行(k) = (lane >> 4) × 4，共 4 个
n=0n →15
C · accumulator int32
列(n) = lane & 15
行(m) = (lane >> 4) × 4 + e
n=0n →15

三者的 lane 分解其实是同一个：

lane & 15 决定lane >> 4 决定
A行 mk 组
B列 nk 组
C列 n行组 m/4

最容易弄错的一点：lane 供给的 A 行号，不是它持有的 C 行号。 lane L 供给 A[L&15][…]，却接收 C[(L>>4)×4+e][L&15]。 同一个 L&15 在 A 里是行号，在 C 里是列号。 试试 lane 0 和 lane 16：两者的 A 行都是 0、C 列都是 0，但 C 行组一个是 0–3、一个是 4–7。 数据在 MMA 单元内部跨 lane 流动，不是每条 lane 各算自己那份。

k 的顺序其实是乱的，而这没关系

  

    按上面的读法，lane L 在 (c,w) 这一对下标上拿到的逻辑 k 是
    (L>>4)×16 + c×64 + w×4（c 是 k 组，w 是 16B 里的第几个 word）。
    但硬件认为 lane L 在一条指令里提供的是该指令 16 宽窗口内的 k0 = (L>>4)×4。
    两者并不相等 —— 送进 MMA 的 k 顺序被打乱了。

    为什么结果还是对的：k 方向是求和。只要 A 和 B 用同一个置换，
    每条指令配对的始终是正确的 (A[m][k], B[n][k])；
    而 16 条指令的 k 集合合起来恰好覆盖 0..255 各一次，总和就等于真正的点积。
  

  

    k = 64·c + 16·q + 4·w + j —— 四个独立的位段，这就是一个混合基数分解，天然是双射。
    c,w,j ∈ 0..3 来自代码结构，q = lane/16 来自硬件，四者合起来恰好铺满 0..255。
  


  

    

      这个认识省掉的是 B 的转置 —— 让 A 和 B 承受同样的错乱，错乱就互相抵消，
      代价是零。只要别只对其中一个做重排。
    

    

      但它不顺带解决 LDS bank 冲突：那是另一回事。本页这个 128×128 的 tile 里，
      取片段时 16 条 lane 读的是相邻 16 行的同一个 16B 位置，行距 256B = 64 个 word，
      而 64 是 32 的整数倍 —— 16 条 lane 落在同一组 bank 上。
      kernel_test_v1.cu 里那句「读侧(LDS) 坐标 (标准 XOR)」的注释下面其实没有 XOR，
      就是这个位置。要消掉它得在 LDS 下标上做异或重排，见下一节末尾。

完整 kernel

  

    布局与 kernel_test_v1.cu 逐项一致，只把工程手段换成最朴素的写法：
    异步 ldg_b128_bsm_predicator → 普通 16B 指针拷贝，
    arrive_gvmcnt + barrier_inst → __syncthreads()。
    下标算式、tile 尺寸、wave 排布、写回公式一个字没改。
  


// TILE_M=TILE_N=128  TILE_K=256  THREADS=256  WAVE_M=WAVE_N=2
__global__ void mma_teach_256(const int8_t *__restrict__ A,
                              const int8_t *__restrict__ B,
                              int32_t *__restrict__ C, int M, int N, int K) {
  extern __shared__ int8_t smem[];       // 64KB = A 128x256 + B 128x256
  int8_t *As = smem, *Bs = smem + 128 * 256;

  const int tid = threadIdx.x;            // 0..255
  const int wave = tid / 64, lane = tid % 64;
  const int wave_m = wave / 2, wave_n = wave % 2;   // wave 的 2x2 排布
  const int block_row = blockIdx.y * 128;  // 本 block 负责的 M 起点
  const int block_col = blockIdx.x * 128;  // 本 block 负责的 N 起点

  i32x4 acc[4][4];
  for (int m = 0; m < 4; ++m)
    for (int n = 0; n < 4; ++n) acc[m][n] = (i32x4){0, 0, 0, 0};

  const int ld_row = tid / 16;            // 搬运:16 线程合搬一行
  const int ld_k = (tid % 16) * 16;
  const int mn = lane % 16;               // 取片段:tile 内行/列
  const int q = lane / 16;                // k 组

  for (int tk = 0; tk < K / 256; ++tk) {  // K=256 时只走一轮
    // --- 1. global -> LDS,每线程 16B,8 轮铺满 128 行 ---
#pragma unroll
    for (int i = 0; i < 8; ++i) {
      const int r = ld_row + i * 16, koff = tk * 256 + ld_k;
      *(i8x16 *)&As[r * 256 + ld_k] = *(const i8x16 *)&A[(block_row + r) * K + koff];
      *(i8x16 *)&Bs[r * 256 + ld_k] = *(const i8x16 *)&B[(block_col + r) * K + koff];
    }
    __syncthreads();

    // --- 2. LDS -> 寄存器,32 条 16B 读 = 64+64 个片段 ---
    i8x16 af[4][4], bf[4][4];
#pragma unroll
    for (int s = 0; s < 4; ++s)
#pragma unroll
      for (int c = 0; c < 4; ++c) {
        const int k_off = q * 16 + c * 64;
        af[s][c] = *(const i8x16 *)&As[(wave_m * 64 + s * 16 + mn) * 256 + k_off];
        bf[s][c] = *(const i8x16 *)&Bs[(wave_n * 64 + s * 16 + mn) * 256 + k_off];
      }

    // --- 3. 4 x 4 x 4 x 4 = 256 条 MMA ---
#pragma unroll
    for (int m = 0; m < 4; ++m)
#pragma unroll
      for (int n = 0; n < 4; ++n)
#pragma unroll
        for (int c = 0; c < 4; ++c)
#pragma unroll
          for (int w = 0; w < 4; ++w)
            acc[m][n] = __builtin_mxc_mma_16x16x16i8(af[m][c][w], bf[n][c][w], acc[m][n]);
    __syncthreads();
  }

  // --- 4. 写回:四层偏移一层层加,这就是归属的权威定义 ---
  const int cm = (lane / 16) * 4, cn = lane % 16;
#pragma unroll
  for (int m = 0; m < 4; ++m)
#pragma unroll
    for (int n = 0; n < 4; ++n) {
      const int row = block_row + wave_m * 64 + m * 16 + cm;
      const int col = block_col + wave_n * 64 + n * 16 + cn;
#pragma unroll
      for (int e = 0; e < 4; ++e) C[(row + e) * N + col] = acc[m][n][e];
    }
}

再往上还差什么

  

    到这一步，布局已经和生产 kernel 一致了，欠的全是延迟与冲突这类工程问题：
  

  
    
    
  1. LDS bank 冲突：取片段时 16 条 lane 落在同一组 bank（上一节末尾那段）。
      要在 LDS 下标上做异或重排。
    2. 
    
  2. 访存延迟暴露：这里是 global 读 → LDS 写 → sync → MMA，
      global 的几百周期全在关键路径上。改成先发下一轮的 global 读、再做 MMA，
      用 256 条 MMA 的时间盖住它。
    3. 
    
  3. 驻留度：64KB LDS 意味着一个 CU 只放得下一个 block，靠并发掩盖不了延迟 ——
      这也是上一条必须做的原因。
    4. 
  

  

    这三样在 tutorial_i8_256_v2.cu / _v3.cu 里都做了（swizzle、
    寄存器转置、global→寄存器预取），可以对照着看。
