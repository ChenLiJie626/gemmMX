双缓冲为什么反而更慢

上一篇把 LDS 读的 bank 冲突消掉之后，瓶颈换成了「搬运和计算没有重叠」。 教科书答案是双缓冲：一个窗口在算，另一个窗口在搬。 我把它做出来了，而且它比单缓冲慢 1.6 倍。 原因不在流水线本身，在它要的那第二份 LDS —— 64KB 一满，每个 CU 就只驻留得下一个 block。 真正该做的是一行位置的改动：把搬运的发射挪到 LDS 读完之后， 单缓冲照样重叠，一个字节额外 LDS 都不要。 4096³：153.5 → 292 TOPS。

双缓冲（733 us）比单缓冲晚发射最差的那次（515 us）还慢 1.42 倍。 两者的 LDS 用量是 64KB 对 32KB，驻留 block 数是 1 对 2 —— 这是实测的（mcOccupancyMaxActiveBlocksPerMultiprocessor），不是推的。 双缓冲买到的 block 内重叠，远不够赔它损失的跨 block 重叠。

01

先看清「没有重叠」长什么样

上一篇结尾那版代码的形状是这样的： 

for (每个 k 窗口) {
    发异步读 -> buf          // 16 条 BSM
    arrive_gvmcnt(0);        // ← 立刻等全部回来
    barrier;
    读 buf -> 寄存器
    256 条 MMA
    barrier;
}

发出去和等回来之间什么都没有。异步搬运的本事是「发了先不管，去干别的」， 可这里发完下一句就是等，和同步拷贝没有区别 —— 这也正是上一篇里「异步单独上只值 1.1%」的原因。

要让它赚到钱，得在「发」和「等」之间塞进计算。有两条路：

02

单缓冲也能重叠：把发射挪到读完之后

这是最容易被跳过的一步。直觉上「要重叠就得双缓冲」， 但其实单缓冲也能重叠，只要想清楚一件事：

LDS 这块地，在「读进寄存器」那一刻之后就没人要了。 后面 256 条 MMA 全在寄存器上跑，一次都不回头碰 LDS。 所以读完之后就可以往上覆盖下一窗 —— 不需要第二块地。

唯一要小心的是：得等所有人都读完，才能覆盖。所以中间多一个 barrier：

for (每个 k 窗口) {
    arrive_gvmcnt(0);        // 等上一轮发的那批（不是刚发的）
    barrier;                 // barrier A
    读 buf -> 寄存器
    barrier;                 // barrier B：确认大家都读完了，可以覆盖
    发异步读 -> buf           // ← 挪到这里
    256 条 MMA               // ← 和上面那批搬运重叠
}

改动只是把发射那几行往下挪了两行，外加循环前预取第 0 窗。 LDS 一个字节没多要，TK=256 下就值 1.20×。

03

双缓冲：看起来更漂亮，代价在别处

双缓冲就是拿第二块地换掉那个 barrier，顺便让发射能提得更早：

for (每个 k 窗口) {
    cur = tk & 1;  nxt = cur ^ 1;
    arrive_gvmcnt(0);
    barrier;
    发异步读 -> buf[nxt]      // ← 写的是另一块地，读之前就能发
    读 buf[cur] -> 寄存器
    256 条 MMA               // barrier B 不需要了
}

纸面上每项都更好：发射更早、重叠更长、每窗少一个 barrier。 问题是它要两份 LDS，而这个 kernel 的 LDS 早就顶满了： 

TILE_K = 256：一份缓冲 2 × 128 × 256 = 65536 B  // 正好是上限，双缓冲放不下
TILE_K = 128：一份缓冲 2 × 128 × 128 = 32768 B  // 两份 65536 B，正好用满

所以双缓冲必须先把 TILE_K 砍到 128。 砍 TILE_K 不改变总工作量（窗口数翻倍、每窗 MMA 和 LDS 读都减半）， 但它改变了一件要命的事 —— 看下一节。

04

真正的账：那 64KB 买的是 block，不是缓冲

LDS 是按 block 整块分配的，所以一个 block 用多少 LDS， 直接决定一个 CU 上能同时驻留几个 block。这是实测值： 

$ ./mma_pipeline_256 occ

设备 MetaX C500：104 个 CU，每 block LDS 上限 65536 B

  组合                    LDS/block 驻留 block/CU
  TK=256 顶部发射(无重叠)      65536              1
  TK=256 单缓冲晚发射          65536              1
  TK=128 顶部发射(无重叠)      32768              2
  TK=128 单缓冲晚发射          32768              2
  TK=128 双缓冲                65536              1

所以这笔账是这么算的。 双缓冲买到的是一个 block 内部的搬运/计算重叠； 它赔掉的是两个 block 之间的重叠 —— 而后者是硬件白送的，覆盖面还更宽（不光盖搬运，连 MMA 之间的气泡、barrier 的等待都能盖）。 在这张卡上，白送的那个明显更值钱。

回头看第 00 节那张表，每一行都能用「驻留几个 block」解释： 1 个 block 的三行是 153.5 / 185.0 / 187.6 TOPS， 2 个 block 的两行是 235.3 / 267–322 TOPS。 占用率这条线，比流水线写得好不好那条线陡得多。

05

一个要说清楚的不稳定

五个组合里有四个跨进程重复得非常死（极差 < 2.2%）， 但最快的那个不是：

TK=128 双缓冲732.3 ‥ 733.30.1%

同一个二进制、同一份输入，只是重启进程，就在 427 和 515 之间跳 （样本：427.1 / 427.5 / 426.7 / 470.8 / 472.6 / 486.0 / 514.7）。 每次进程内部两轮是对得上的（差 < 0.3%），所以不是测量噪声， 是这个配置本身对两个 block 怎么排进 CU敏感。 我没有继续挖下去 —— 要定位得看调度器的落位，这页给不出结论。

为什么这不影响结论。就算每次都落在最差的 514.7 us， 它仍然比双缓冲的 733 us 快 1.42×，比基准快 1.73×。 名次一次都没变过。所以表里给的是区间而不是最好成绩。
