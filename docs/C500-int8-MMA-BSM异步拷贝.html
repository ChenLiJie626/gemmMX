BSM 异步拷贝的真身

前三篇一直在用 __builtin_mxc_ldg_b128_bsm_predicator 搬数据， 却没人说得清它那十个实参各是什么。这一篇把它一路扒到真实的 MetaX 汇编 —— 不用装任何东西，汇编打印器本来就在 mxcc 里。 结果：十个实参在机器上只剩一条指令， 其中落点只传第一条 lane 的那一个地址（这才是「必须按线程号连续」的真正原因， 违反了不报错、数值静默错位），四个布尔开关里只有一个在汇编里留下痕迹， 而我们写的那句 arrive —— 编译器一条等待都没替我们插。

00

结论速查

问题汇编给的答案
十个实参变成什么一条指令：ldg_b128 r0, s4, r1, 0x0 ret0_en bsm pred_reg:s2，外加三条准备指令（算谓词、取落点、塞 md）
源地址标量基址 s4 + 每条 lane 自己的偏移 r1（向量）
落点地址只有一个标量：rfl_b32（读第一条 lane）取出来塞进 md。其余 63 条 lane 算的落点被丢掉
谓词pred_reg:s2，cmp_lt_i32 算出的 64 位 lane 掩码
F1（SDK 叫 Ret0）汇编里的 ret0_en 修饰符。谓词假时写零，去掉则原样不动
F2 / F3 / F4F3 把谓词取反（行为实测）。F2、F4 在汇编文本里没有任何痕迹 —— 我们和 SDK 传的 F4 不同，生成的指令逐字相同
我们写的 arrive_gvmcnt(0)arrive gvmcnt(0)，真实存在；三级流水那档是 arrive gvmcnt(4)
不写 arrive 会怎样编译器不会替你插 —— 汇编里 ldg_b128 后面直接就是 lds_u8。之前「删掉也全对」只能解释为延迟来得及

01

怎么拿到真汇编：不用装，它一直在

mxcc 的驱动层不收 -S，工具链里也没有 llc、没有 llvm-objdump，设备 ELF 的 e_machine 还借成了 Synopsys ARCv3（系统 objdump 认不了）。 看上去只能到 IR 为止 —— 但 mxcc 本身就是 clang， mxcc -cc1 能直接当前端用，而 cc1 接受 -x ir， 于是它就是一个现成的 llc： 

mxcc -x maca -O3 -offload-arch native --maca-path=/opt/maca -fatbc a.cu -o o.bc
clang-offload-bundler --type=bc --unbundle --input=o.bc \
    --targets=maca-mxc-metax-macahca--xcore1000-bc --output=d.bc
llvm-dis d.bc -o d.ll
mxcc -cc1 -triple mxc-metax-macahca -target-cpu xcore1000 -S -O3 -x ir d.ll -o d.s

出来的是真东西，连 kernel 的资源描述段都在：

probe_ours:
        ldu_b128 s4, s0, 0x0
        ...
        ldg_b128 r0, r4, 0x0 ret0_en bsm pred_reg:s2
        arrive gvmcnt(0)
        barrier
        endk
        .macahca_kernel probe_ours
                .macahca_mtreg_size 1
                .macahca_streg_size 1
                .macahca_bsm_size 0
                .macahca_warps_per_dpc 416
        .end_macahca_kernel

02

一条指令的解剖

十个实参，到机器上就是这么一条：

注意这个不对称：源地址是向量的，落点是标量的。 64 条 lane 各取各的 16 B（所以全局侧可以随便换人取 —— 这正是 XOR 能挪到全局侧的原因）， 但它们共用一个落点基址。下一节说明这件事有多要命。

03

落点只传一个标量 —— 这才是那条约束的真正原因

前几篇一直照抄「BSM 的 LDS 落点必须按线程号连续」，当时只有基线代码这一个依据。 汇编把原因摆出来了： 

rfl_b32  s1, r2        // r2 是每条 lane 自己算的落点；rfl = 读第一条 lane
smov_b32 md, s1        // 把这个标量塞进 md
ldg_b128 r0, s4, r1, 0x0 ret0_en bsm pred_reg:s2

rfl_b32 只取第一条 lane 的值，其余 63 条算出来的落点 在这里被直接丢掉。硬件拿到这一个基址之后，按 lane 号往后连续铺 16 B。 所以「连续」不是一条建议，是这条指令唯一能表达的东西。

验证：故意把落点在组内打乱，看汇编和数值各是什么反应。

这条也就解释了为什么 XOR 必须挪到全局侧。 源地址是向量的（每条 lane 可以取不同的块），落点是标量的（只能连续）。 想做 swizzle，就只能动「这条 lane 去取哪一块」，不能动「这条 lane 写到哪个槽位」。 前一篇是靠异或的对合性质绕过去的，现在知道那不是取巧，是唯一的走法。

04

十个实参，五个操作数，一条指令

先看 IR 这一层它长什么样（llvm-dis 的原文）：

%13 = tail call i64 @llvm.mxc.icmp.i64.i32(i32 %koff, i32 %K, i32 40)
%14 = tail call <4 x i32> @llvm.mxc.ldg.predicator.bsm.v4i32(
        ptr addrspace(3) %6, ptr addrspace(1) %12, i32 0, i64 %13,
        i1 true, i1 true, i1 false, i1 true)

为什么是 i64。一个 wave 64 条 lane，一位一条。 所以这不是「一个条件」，是 per-lane 的谓词 —— 同一条指令里，有的 lane 搬、有的 lane 不搬。

05

四个开关：真值表，以及汇编里的对照

SDK 自带的包装器传的是 (Ret0=false, true, false, false)， 我们（抄 kernel_test_v1.cu）传的是 (true, true, false, true) —— 第 1 个和第 4 个不一样。先看行为：

  我们写的   (1,1,0,1)  lane32=零          | 数据 32 哨兵  0 零 32
  SDK 包装器 (0,1,0,0)  lane32=哨兵(没动)  | 数据 32 哨兵 32 零  0
  只翻 F1    (0,1,0,1)  lane32=哨兵(没动)  | 数据 32 哨兵 32 零  0
  只翻 F4    (1,1,0,0)  lane32=零          | 数据 32 哨兵  0 零 32
  只翻 F2    (1,0,0,1)  lane32=零          | 数据 32 哨兵  0 零 32
  只翻 F3    (1,1,1,1)  lane0=零 lane32=数据   ← 谓词被取反

再把两种标志组合的汇编 diff 一下，整段函数只差一个修饰符：

< ldg_b128 r0, r4, 0x0 ret0_en bsm pred_reg:s2      // 我们 (1,1,0,1)
> ldg_b128 r0, r4, 0x0         bsm pred_reg:s2      // SDK  (0,1,0,0)

F4 连一个比特的痕迹都没留下。两组标志的 F4 是不同的 （我们 1、SDK 0），而生成的指令逐字相同 —— 行为实验说「没观察到影响」，汇编把话说死了：在这条路径上它什么都不控制。

而 F1 的差异在我们的用法里永远不触发： kernel 里 koff = tk*TILE_K + j*16 恒小于 K，谓词全真。 实测整组换成 SDK 的标志，八个组合数值完全一致，4096³ 七档计时持平（< 0.3%）。 反过来说，整套谓词机制在我们这儿是空转的，每条 BSM 白搭一条 cmp_lt_i32；想省就换不带 predicator 的版本。

06

返回值：会把编译器弄崩

它返回 <4 x i32>（汇编里就是那个没人用的 r0）。 我们一直丢弃。一旦接住，编译器后端当场崩：

error: Illegal instruction detected: Operand has incorrect register class.
$mtreg_64bits_2 = SHL_B64 0, $amtreg_64bits_0, implicit $xmsk,
                  implicit-def $mtreg_128bits_2, implicit $amtreg_128bits_0

07

真正的硬前提：16B 对齐

b128 一次搬 16 B，两头都要 16 B 对齐。LDS 那头没问题 （落点恒为 tid*16 + i*(一轮字节数)）；global 这头要看调用者： 

src = &A[(size_t)ga * K + koff]
      ga * K  要 16B 对齐  ->  K % 16 == 0
      koff    恒为 16 的倍数   koff = tk*TILE_K + j*16
      A 本身   mcMalloc 给 256 B 对齐，没问题

K 不是 16 的倍数时这就是真 UB，不编译报错也不运行报错。 本仓库的 main 挡的是 K % 256 == 0，顺带盖住了这件事 —— 把这个 kernel 搬去别处，这是第一条要重新检查的前提。

08

那句 arrive：编译器没替我们插任何等待

我们写 arrive_gvmcnt(0)（__builtin_mxc_arrive(64)）， 而 SDK 的 __pipeline_wait_prior 忽略它的参数， 永远发 arrive(0x3040)。先确认我们这句是真的：汇编里是 arrive gvmcnt(0)，三级流水那档是 arrive gvmcnt(4) —— 部分等待确实是一条真指令，计数也对得上 （(NBUF-2) × 每线程每窗 4 条 BSM）。
