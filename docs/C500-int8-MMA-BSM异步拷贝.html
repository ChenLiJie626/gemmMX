BSM 异步拷贝的真身

前三篇一直在用 __builtin_mxc_ldg_b128_bsm_predicator 搬数据， 但没人说得清它那十个实参各是什么。这一篇把它扒开： 十个实参在 IR 里其实只有五个操作数，末尾三个会被折成一条 icmp，产出一个一位一条 lane 的 64 位掩码； 四个布尔开关里只有两个真的有用，而我们和 SDK 自带包装器传的正好不一样。 顺带挖出三件事：接住它的返回值会让编译器后端直接崩、 真正的硬前提是 16B 对齐而不是那些开关、 以及那句 arrive 并不是这些 kernel 算对的原因。

00

结论速查

问题答案
十个实参是什么前两个是指针（必须分别是 LDS 和 global），第三个是偏移，第 4~7 个是四个布尔开关，最后三个合起来是一条比较（左、右、比较符），在 IR 里折成一个 i64 掩码
掩码是什么粒度一位一条 lane，i64 正好覆盖一个 wave 的 64 条
F1（SDK 叫 Ret0）谓词为假时：1 = 把那 16 B 清零，0 = 原样不动
F3把谓词取反。设错了结果直接全错
F2 / F4单独翻转无任何可观察影响（实测）
我们和 SDK 传的一样吗不一样：我们 (1,1,0,1)，SDK 包装器 (0,1,0,0)
那会出事吗不会。唯一有行为差别的是 F1，而我们的 kernel 里谓词恒为真，这个差别永远不触发。实测换成 SDK 的标志，八个组合数值完全一致
真正的雷① 接住返回值 = 编译器后端崩；② K % 16 != 0 时 global 侧未对齐，这才是真 UB；③ arrive 的实际作用说不清

01

怎么扒：能看到的最低一层是 IR

这台机器上没有设备 ISA 反汇编器。mxcc 不收 -S， 工具链里没有 llc，而 -device-bin 吐出来的设备 ELF 把 e_machine 借成了 Synopsys ARCv3，系统 objdump 认不了。 能走到的最低一层是 LLVM IR： 

mxcc -x maca -O3 -offload-arch native --maca-path=/opt/maca -fatbc a.cu -o o.bc
clang-offload-bundler --type=bc --unbundle --input=o.bc \
    --targets=maca-mxc-metax-macahca--xcore1000-bc --output=d.bc
llvm-dis d.bc -o d.ll

02

十个实参，五个操作数

我们源码里是这么写的：

__builtin_mxc_ldg_b128_bsm_predicator(
    As + dst,                          // 1  LDS 落点
    (void *)&A[(size_t)ga * K + koff], // 2  global 源
    0, true, true, false, true,        // 3  偏移 + 4..7 四个开关
    koff, K, CMP_SLT);                 // 8,9,10  ← 其实是一条比较

IR 里它长这样（llvm-dis 的原文）：

%13 = tail call i64 @llvm.mxc.icmp.i64.i32(i32 %koff, i32 %K, i32 40)
%14 = tail call <4 x i32> @llvm.mxc.ldg.predicator.bsm.v4i32(
        ptr addrspace(3) %6, ptr addrspace(1) %12, i32 0, i64 %13,
        i1 true, i1 true, i1 false, i1 true)

declare <4 x i32> @llvm.mxc.ldg.predicator.bsm.v4i32(
    ptr addrspace(3) noalias nocapture, ptr addrspace(1) noalias nocapture,
    i32 immarg, i64, i1 immarg, i1 immarg, i1 immarg, i1 immarg)

为什么是 i64。一个 wave 64 条 lane，一位一条。 所以这不是「一个条件」，是 per-lane 的谓词 —— 同一条指令里，有的 lane 搬、有的 lane 不搬。

03

四个开关：真机真值表

SDK 自带的包装器是这么调的（__clang_maca_device_functions.h）： 

template <int CopySize, int CmpFlag, bool Ret0 = false>
memcpy_async_pred(void *dst_shared, void *src_global, int cmp_op1, int cmp_op2) {
  return __builtin_mxc_ldg_b128_bsm_predicator(dst_shared, src_global, 0, Ret0,
                                               true, false, false, cmp_op1,
                                               cmp_op2, CmpFlag);
}

逐位对一下：SDK 是 (Ret0=false, true, false, false)， 我们（抄的 kernel_test_v1.cu）是 (true, true, false, true) —— 第 1 个和第 4 个不一样。于是写个探针逐个翻转，LDS 预填哨兵 0x7E7E7E7E，K=512 让一半 lane 的谓词为假： 

  我们写的   (1,1,0,1)  lane32=零          | 数据 32 哨兵  0 零 32
  SDK 包装器 (0,1,0,0)  lane32=哨兵(没动)  | 数据 32 哨兵 32 零  0
  只翻 F1    (0,1,0,1)  lane32=哨兵(没动)  | 数据 32 哨兵 32 零  0
  只翻 F4    (1,1,0,0)  lane32=零          | 数据 32 哨兵  0 零 32
  只翻 F2    (1,0,0,1)  lane32=零          | 数据 32 哨兵  0 零 32
  只翻 F3    (1,1,1,1)  lane0=零 lane32=数据   ← 谓词被取反

所以我们和 SDK 的差异，在我们的用法里永远不触发。 kernel 里 koff = tk*TILE_K + j*16，而 tk < K/TILE_K， 所以 koff < K 恒成立 —— 谓词全真，F1 管的那条分支根本走不到。 实测把标志整组换成 SDK 的那一套，八个组合数值完全一致， 4096³ 下七档计时逐项持平（< 0.3%）。

反过来说：整套谓词机制在我们这儿是空转的， 每条 BSM 白搭一条 icmp。真想省，换成不带 predicator 的 __builtin_mxc_ldg_b128_bsm 就行。

05

真正的雷之二：对齐，而不是那些开关

b128 一次搬 16 B，两头都要 16 B 对齐。 LDS 这头没问题：落点恒为 tid*16 + i*(一轮字节数)（这也正是 BSM 要求的 「按线程号连续」，前一篇验过）。global 这头要看调用者： 

src = &A[(size_t)ga * K + koff]
      ga * K  要 16B 对齐  ->  K % 16 == 0
      koff    恒为 16 的倍数   koff = tk*TILE_K + j*16
      A 本身   mcMalloc 给 256 B 对齐，没问题

所以 K 不是 16 的倍数时，这就是真的 UB， 而且没有任何东西会提醒你 —— 不会编译报错，不会运行报错。 我们的 main 里挡的是 K % 256 == 0（因为 TILE_K 最大 256）， 顺带把这件事盖住了。把这个 kernel 搬去别处时，这是第一条要重新检查的前提。

另外两个小地方：签名要的是 void *，所以源指针那个 (void *) 转换丢掉了 const —— 它只读，无害， 但这是 SDK 签名的毛病，不是我们能修的。还有 IR 上那对 noalias nocapture：两个指针本来就在不同地址空间，不会互相别名。

06

那句 arrive 到底在不在等

我们一直写 arrive_gvmcnt(0)，也就是 __builtin_mxc_arrive(64)。 但 SDK 自己的 __pipeline_wait_prior 是这样的： 

__CG_STATIC_QUALIFIER__ void __pipeline_wait_prior(size_t prior) {
  __builtin_mxc_arrive(0x3040); // arrive 0
}

它把 prior 整个忽略了，永远发 0x3040。 注意 0x3040 = 0x3000 | 0x40，而我们的 64 = 0x40 正好是那个低字节 —— 看着像同一个字段的不同填法，但高位那 0x3000 是什么，源码里没有任何线索。 所以直接做对照实验：把等待全删掉，再让一条 lane 去读 另一条 lane 搬进来的数据（这样编译器推不出依赖）。

这推翻了上一篇的一句话。上一篇说排空阶段的修正是必需的， 依据是 host 上的逐步模拟。模拟证明的是「按 gvmcnt 的契约会违约」， 不是「真机会算错」—— 真机没复现。

现在只剩两种解释：后端在 LDS 读之前自己插了等待，或者延迟总是来得及。 要分辨得看 ISA，而这台机器上看不到（见第 01 节）。 所以那个修正该留着 —— 让代码守契约，而不是依赖一个没写进文档、 也查不出机理的兜底 —— 但不能说它是这些 kernel 算对的原因。

07

那我们的写法要不要改

这件事要不要改为什么
F1=1 和 SDK 的 0 不一致不用谓词恒真，差别不触发；实测换过，八个组合数值一致
F4=1 和 SDK 的 0 不一致不用单独翻转无任何可观察影响
谓词整套是空转的可以改换成不带 predicator 的版本，每条 BSM 省一条 icmp；没测过值多少
返回值千万别接接住就编译崩
K % 16必须挡global 侧未对齐，静默 UB
arrive留着实测不花钱，而且它是唯一有文档形态的契约
