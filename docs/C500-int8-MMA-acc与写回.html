acc 在哪，第四步要不要等

__builtin_mxc_mma_16x16x16i8 看着像一条普通的三操作数指令， 于是很容易读成「每条 lane 算自己那份，再累加到某个公共的地方」。 这个读法两头都不对。 acc 是纯线程私有的寄存器，没有任何公共累加器； 但这条指令也不是 64 个独立的标量运算 —— 它是一次 wave 级的集体操作，数据横穿 lane。 这页把这两件事和「第四步要不要等」一起理清楚。

00

三个问题，先给短答案

问题答案
一条 lane 的 fragment 过一次 MMA，能得到完整的 wave 子矩阵吗？ 不能，差得远。一条 MMA 只算 wave 区域 64×64 里的一个 16×16 tile，而且这个 tile 的 256 个结果摊给 64 条 lane，每条只拿 4 个。整个 wave 区域要 256 条 MMA
是不是每条 lane 把自己的 fragment「累加到全局」？ 不是。没有全局累加器，没有 atomic，没有归约。acc 是线程私有寄存器，从头到尾只有本 lane 读写
acc 是全局维度的还是线程私有的？ 线程私有。但「一条 lane 的 acc 里装的是哪几个 C 元素」由硬件定死，不是我们挑的
一条 MMA 的「16 个 k」，是一个 C 元素需要的全部 k 吗？ 不是，远远不是。一条 MMA 只跨 16 个 k，出的是部分和。一个 acc[m][n] 要 16 条 MMA 才凑满一个 k 窗口（16 × 16 = 256），K 更大时还要跨 K/256 个窗口继续累。详见第 03 节
到第四步时 wave 子矩阵算完了吗？ 算完了。k 循环一出来，acc 就是终值
第四步需要等 acc 全部算完吗？ 不需要 barrier。每条 lane 只写自己的 acc、只写自己独占的地址。代码里写回前也确实一个 barrier 都没有

01

acc 在哪：就是普通的私有寄存器

先把最容易误会的一点钉死。声明长这样：

i32x4 acc[MMA_M][MMA_N];        // 4 × 4 个累加器，每个 4 个 int32
...
acc[m][n] = __builtin_mxc_mma_16x16x16i8(af[m][c][w], bf[n][c][w], acc[m][n]);
//   ↑ 读自己的，写自己的。没有指针，没有 __shared__，没有 atomic

它就是个局部变量，住在寄存器里。没有任何「全局维度」的累加器存在 —— 不存在一块 C 的暂存区被 64 条 lane 轮流加。 kernel 从头到尾只碰一次 C，就是第四步那几条 store。

那为什么还是集体操作？因为私有的是存储，不是运算。 acc 的读写确实只有本 lane；但这条指令在执行时， 硬件会把全部 64 条 lane 的 a 和 b 寄存器一起读走， 算完整的 16×16×16，再把 256 个结果按另一套固定映射发回 64 条 lane 的 acc。 所以：存储是私有的，数据流是横穿 lane 的。

02

一条 MMA 指令里到底发生了什么

把一条指令的账算一遍就清楚了。每条 lane 交进去 a、b 各 4 个 int8：

为什么必须交叉？因为一条 lane 的寄存器只有 32 位 = 4 个 int8， 而一条 MMA 要出它那一份部分和，需要它负责的那 16 个 k 同时在场。 这 16 个 k 被切成 4 段分给 4 条 lane，所以一个输出格子的原料天生就散在好几条 lane 手里 —— 没有任何一条 lane 能独自算出任何一个输出。

注意这里的「16 个 k」只是一条指令的胃口，不是一个 C 元素的全部需求。 指令名 mma_16x16x16 最后那个 16 就是它一次吃多少 k。 一个 C 元素的终值要 K 个 k —— 那是靠很多条 MMA 累加到同一个 acc 得到的。 这是最容易混的一处，下一节专门算这笔账。

拿 lane 19 当例子（p = 3，q = 1）：

公式lane 19 实际拿到/交出
交 a行 = p，k = 4q‥4q+3A[3][4‥7]
交 bk = 4q‥4q+3，列 = pB[4‥7][3]
领 acc行 = 4q+e，列 = pC[4][3] C[5][3] C[6][3] C[7][3]

看最后一行：C[5][3] 归 lane 19。 可 lane 19 交进去的 A 是第 3 行，它从头到尾没见过 A 的第 5 行。 算 C[5][3] 要用的 A[5][0‥15]，是 lane 5 / 21 / 37 / 53 交的。 这就是「数据横穿 lane」最直白的证据 —— 也是真机 dump 验过的（第 06 节）。

03

「16 个 k」说的是一条指令，不是一个元素

这是读这套东西最容易卡住的一处，值得单独算清楚。 一条 MMA 不产出终值，它产出的是部分和： 

// 一条 MMA 干的事（注意是 += ）
C_tile[16][16] += A_tile[16][16] × B_tile[16][16]
//                            ↑ 这个 16 就是 k 的跨度：一条指令只吃 16 个 k

// 一个 C 元素的终值
C[m][n] = Σ(k = 0 .. K-1) A[m][k] · B[n][k]
//        ↑ 要 K 个 k。K=256 就是 256 个，一条指令差得远

所以两边要对上，靠的是往同一个 acc 上反复累加。账是这样的：

层级覆盖多少 k为什么
1 条 MMA16指令本身的跨度。4 条 lane 各交 4 个 int8，4 × 4 = 16
1 个 acc[m][n]，1 个 k 窗口16 × 16 = 256内层 c(0‥3) × w(0‥3) = 16 条 MMA 累到同一个累加器，正好铺满 TILE_K = 256
1 个 acc[m][n]，完整的 KK再乘上 K / 256 个 k 窗口。acc 跨窗口不清零，一路累下去

那 16 条 MMA 各自覆盖哪 16 个 k？不是连续的 16 个， 而是按 k = 64c + 16q + 4w + j 散成四段 4 连号 （q 是 lane 的那一维，j 是一条 lane 手里 4 个 int8 的下标）：

所以你那句话是对的，我原来那句写糙了。 一个 16×16 的 acc tile 要出终值，确实要跨过完整的 K； 原文「算一个 C[m][n] 要 16 个 k 全齐」漏掉了「一条指令的」这个限定， 读起来像在说一个 C 元素只要 16 个 k 就够。已经改掉了。 准确的说法是：一条 MMA 要出它那份部分和，需要它负责的那 16 个 k 同时在场 —— 「同时在场」才是那句话的重点，它解释的是为什么 k 必须切开分给 4 条 lane， 而不是在说一个元素总共需要多少 k。

顺带对一下别处的数：wave 每个 k 窗口 256 条 MMA = 16 个累加器 × 每个 16 条。这和第 04 节「每条 lane 持 16 个累加器」是同一笔账的两个方向。

05

第四步：算完了吗？要等吗？

算完了。k 循环退出的那一刻，每个 acc[m][n][e] 已经是完整的点积 —— K 个乘积全加完了，没有尾巴。第四步纯粹是搬运，不含任何运算。

不需要 barrier。三条理由，缺一不可：

代码里也确实没有。mma_teach_256.cu 第 128–131 行：

            acc[m][n] = __builtin_mxc_mma_16x16x16i8(af[m][c][w], bf[n][c][w],
                                                     acc[m][n]);
    __syncthreads();        // ← 128 行：这是循环体里的最后一句
  }                         // ← 129 行：k 循环到此结束
                            // ← 130 行：空行。没有 barrier。
  // ---- 4. 写回 ----      // ← 131 行：直接开始写

128 行那个 __syncthreads() 容易被误会成「等 acc 算完」。 它不是。它在循环体内，作用是「下一轮要覆盖 LDS 了，先确认这一轮所有人都读完」—— 管的是 As/Bs，和 acc 一点关系都没有。 最后一轮执行的那次，对写回其实没有任何作用。

那么「等」这件事到底在哪一层发生？分三层看，不要混：

层次要不要等靠什么
同一个 acc[m][n] 上的连续 MMA 要 串行依赖（后一条吃前一条的结果），硬件记分板自动处理，不用写一个字
同一条 MMA 里的 64 条 lane 天然同步 一条 wave 共用一个 PC，这条指令本身就是整个 wave 一起执行的，不存在「有的 lane 先到」
acc 终值 → 第四步 store 不要 线程内的寄存器依赖，同样是记分板。跨线程无依赖，所以不需要 barrier
不同 wave 之间 不要 4 个 wave 各管各的 64×64，写的 C 区域互不重叠

一句话：要等的那一层硬件已经替你等了，不用等的那几层本来就没有依赖。 写回前真正的前提只有一个 —— 归属公式是双射： (wave, lane, m, n, e) 到 C 元素是一一对应的， 所以 256 个线程同时往 C 里写，没有两条 lane 会撞到同一个地址。 这一条是 prov_256 探针逐元素验过的。
