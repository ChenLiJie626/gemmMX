# tutorial-int8-mma —— C500 int8 MMA 数据排布教程

这个分支不做实现之间的性能横评，只回答一个问题：

> **`__builtin_mxc_mma_16x16x16i8` 这条指令，数据到底是怎么排的？**
> 哪条 lane 交进去什么、拿回来什么，算完之后写回大矩阵的哪一格。

排布讲清楚之后，顺着同一套下标还能看出一处 LDS bank 冲突，
所以分支里也带了消冲突的 XOR swizzle 版本和它的图解。

本分支（`kernel-c600`）在教程分支之上只多一个文件：`mma_swizzle_c600.cu`，
把同一套布局移植到 C600（xcore1500）的 K=32 int8 MMA 上。
**手上没有 C600 真机，那一份未上机验证** —— 依据、假设和自检见下面「C600 移植」一节。

从 `main` 基线分出，与 [`claude`](https://github.com/ChenLiJie626/gemmMX/tree/claude)、
[`codex`](https://github.com/ChenLiJie626/gemmMX/tree/codex) 两个实现分支平行。

精简版只保留八张讲「谁对应谁」的图，按数据流排：三张座位表 → 交进去 ≠ 拿回来 →
一个输出格子是谁凑的 → LDS 读哪儿 → 复用网格 → 定位图 → 一条 lane 的 64 个落点 → 整条链。

XOR swizzle 那份是性能向的续篇：教程讲清布局之后，这份指出同一个布局里
**取片段的 32 条 LDS 读每条要 16 拍，而下限是 8 拍**，原因是行距 256B 恰好是 bank
阵列宽度的整数倍；改法是一个异或 `槽位 = j ^ (r & 7)`，真机实测 1.83×。九张图依次是
bank 的几何 → 冲突现场（哪条 lane 落在哪个 bank、和谁撞）→ 为什么一条指令天生只占
半圈 bank → XOR 表 → XOR 怎么向隔壁那条指令借走另外半圈 → 修好之后 →
BSM 异步搬运要求落点连续，所以异或得提到全局侧去做。

「acc 在哪」那份回答一个概念问题：`acc` 是**线程私有寄存器**，没有任何全局累加器；
但 `__builtin_mxc_mma_16x16x16i8` **也不是 64 个独立的标量运算** —— 它是 wave 级集体操作，
硬件一次读走 64 条 lane 的寄存器。两件事都对才讲得通「lane 19 持有 C[5][3]，
却从没见过 A 的第 5 行」。顺带说清第四步（写回）为什么**前面不需要 barrier**。

双缓冲那份接着往下做，结论是反直觉的：**双缓冲做出来比单缓冲慢 1.6 倍**。
不是流水线写错了，是它要的第二份 LDS 把每 CU 驻留的 block 从 2 个压到 1 个
（`mcOccupancyMaxActiveBlocksPerMultiprocessor` 实测）。真正该做的是把搬运的
发射挪到 LDS 读完之后 —— 单缓冲照样重叠，0 额外 LDS。

## 代码

全部用 `mxcc` 单文件编译，不依赖本仓库其它文件：

```bash
MXCC=/opt/maca/mxgpu_llvm/bin/mxcc
$MXCC -x maca -O3 mma_teach_256.cu -o mma_teach_256
```

| 文件 | 规模 | 作用 |
|---|---|---|
| `mma_teach.cu` | 1 wave，C 只有 16×16 | 最小教学版：没有任何分块，一眼看完一条 MMA |
| **`mma_teach_256.cu`** | 256×256×256 | **教程主线**。布局与 `kernel_test_v1.cu` 逐字一致，只把异步拷贝/屏障换成最朴素写法。内置三个探针 |
| `tutorial_i8_256.cu` | tile 256×256×256 | 性能线 v1，附 `prov` 来源探针 |
| `tutorial_i8_256_v2.cu` | 同上 | v2：B 走寄存器内 4×4 转置，BK 32→64 消除 bank 冲突 |
| `tutorial_i8_256_v3.cu` | 同上 | v3：v2 + 全局→寄存器预取 |
| `kernel_test_v1.cu` | tile 128×128×256 | 对照用的工程版（异步拷贝 + `arrive_gvmcnt`）。**需要 MACA SDK 的 `mctlass/arch/maca_memory.h`**，不在本仓库内 |
| `mma_swizzle_256.cu` | 256×256×256 | **XOR swizzle 版**，搬运走基线的 BSM 异步通路。`template <bool SW, bool ASYNC>` 两个正交开关 = 四个组合，除这两处外逐字相同，所以「异步值多少」和「XOR 值多少」分得开 |
| **`mma_pipeline_256.cu`** | 256×256×256 | **搬运/计算重叠版**（本分支最快）。`template <int TK, int MODE>` = 五个组合：顶部发射 / 单缓冲晚发射 / 双缓冲 × `TILE_K` 256/128。带 `occ` 子命令直接查每 CU 驻留 block 数 |
| `mma_swizzle_c600.cu` | 同上 | **C600（xcore1500）移植版**。与 `mma_swizzle_256.cu` 同一套布局，差别只有一条：MMA 用 K=32 的 `__builtin_mxc_mma_16x16x32i8`。`-DMX_ARCH=500` 可退回 K=16。**没有真机，未上机验证** |

数据约定（八个文件一致）：

```
A: M × K  行主序 int8
B: N × K  行主序 int8     <-- 注意是 [n][k]，host 侧已转置
C: M × N  行主序 int32
```

### 探针

`mma_teach_256.cu` 里三个探针 kernel 与主 kernel 结构逐行相同，只多一句记录，
教程里所有「真机 dump」都出自它们：

```bash
./mma_teach_256                  # 正确性 + 四层来源表
./mma_teach_256 164 81           # 拆解 C[164][81] 的完整来源链      (prov_256)
./mma_teach_256 reads 1 17       # 某条 lane 的 16 条 LDS 读坐标     (reads_256)
./mma_teach_256 partial 164 81   # 某个 C 元素的 16 条部分和逐条累加 (partial_256)
./mma_teach_256 bench [M N K]    # 计时
```

`mma_swizzle_256.cu` 还带一个**不需要 GPU** 的 bank 模型 —— 把 kernel 里那几条寻址宏
原样搬到 host 上数格子，并穷举两项自检：写进去的块 ↔ 读出来的块是否对得上，
以及异或挪到全局侧之后合并访问的足迹有没有变：

```bash
./mma_swizzle_256 banks              # bank 深度直方图 + 布局自检（纯 CPU）
./mma_swizzle_256                    # 四个组合各对一次 CPU 参考
./mma_swizzle_256 bench 4096 4096 4096   # 四个组合的 us / TOPS 并排
```

`mma_pipeline_256.cu` 把「每 CU 驻留几个 block」直接查出来，不用估：

```bash
./mma_pipeline_256 occ               # mcOccupancyMaxActiveBlocksPerMultiprocessor
./mma_pipeline_256 info              # LDS 预算 / 每窗指令条数（纯 CPU）
./mma_pipeline_256                   # 五个组合各对一次 CPU 参考
./mma_pipeline_256 bench 4096 4096 4096
```

## C600 移植（`mma_swizzle_c600.cu`，未上机）

**没有 C600 真机，这一节里凡是没标「实测」的都是推论。** 之所以还能写出这个
kernel，是因为两颗芯片对本算子的差别可以收窄到一条指令上。

### 依据

| 事实 | 来源 |
|---|---|
| SDK 里有 `__builtin_mxc_mma_16x16x32i8`，target feature 门是 `xcore1500\|1520\|1600\|2000` | C500 真机上查 `__clang_maca_mma_functions.h`（**实测**） |
| C500 是 xcore1000；`-offload-arch=xcore1500` 编得过，一跑就 `ErrorNoBinaryForGpu: Couldn't find xcore1000 binary` | **实测** |
| C600 是 XCORE 1.5 架构 | 公开报道 |
| 所以 K=32 的 int8 MMA 在 C600 上应当可用 | **推论** |

LDS 32 bank × 4B、wave 64 lane、BSM 异步搬运、累加器布局 —— 没有任何公开信息
说这些变了，**全部按不变处理，但每一条都落成了编译期断言或开机自检**，
不成立就编译失败 / 报 MISMATCH，而不是算出错数字。

### 读侧一个字都没改

C500：一条 16B 的 LDS 读 = 4 个 4B 片段 = 喂 **4** 条 K=16 MMA。
C600：**同一条 16B 读** = 2 个 8B 片段 = 喂 **2** 条 K=32 MMA。

地址、步长、bank 行为完全相同 → XOR swizzle 原样成立，mask 还是 7。
改的只有「这 16 个字节切成几份」。

而且不必等拿到 K=32 的片段布局文档就能写：硬件只保证 a 的第 i 个字节槽和 b 的
第 i 个字节槽配到同一个 k，**它认为那是第几个 k 我们不关心** —— 这就是教程第 03 节
「k 的置换不影响结果」那条结论的直接复用。指令 `(c, w)` 从 lane q 取 LDS 字节
`64c + 16q + 8w .. +7`，8 条指令铺满一个窗口的 256 个 k，不重不漏（`banks` 子命令里穷举验过）。

### 一个反直觉的后果

每个 k 窗口、每个 wave 的指令账：

| | LDS 读 | MMA | 读 : MMA |
|---|---|---|---|
| C500，K=16 | 32 条 | 256 条 | 1 : 8 |
| C600，K=32 | 32 条 | **128 条** | **1 : 4** |

MMA 条数砍半而读一条没少，**消 bank 冲突在 C600 上比在 C500 上更值钱，不是更不值钱**。

### 上机第一件事

```bash
mxcc -x maca -O3 -std=c++17 --offload-arch=xcore1500 -DMX_ARCH=600 \
     mma_swizzle_c600.cu -o mma_swizzle_c600
./mma_swizzle_c600 arch     # 编译期假设 vs 真机属性，逐行标 OK / MISMATCH
./mma_swizzle_c600 banks    # bank 模型 + 布局/足迹/k 覆盖自检（纯 CPU，不用 GPU）
./mma_swizzle_c600          # 四个组合各对一次 CPU 参考
```

五件待核的事都在文件头列着，每件都写了怎么查：

1. **arch 串**到底是 `xcore1500` 还是 `1520`/`1600`。`MX_ARCH` 只管选 MMA 的 K，换串不用改代码。
2. **`mma_16x16x32i8` 的真实签名**。本文件按「a/b 各是一个 64 位打包」写成 `long`；
   SDK 若写的是 `int2`，加 `-DMX_FRAG64_AS_V2I32`（一条 grep 就能定）。
3. **累加器布局**。输出块还是 16×16，所以极可能和 K=16 逐字相同；不同的话正确性检查立刻 FAIL，改第 4 段两行。
4. **每 block 的 LDS 上限 / CU 数 / 驻留度**。`arch` 子命令打出来。
5. **BSM 异步搬运**是否同名同语义。不是就 `-DMX_HAS_BSM=0` 退回同步拷贝，XOR 侧不受影响。

正确性**全 FAIL 且四个组合一模一样** → 先怀疑 acc 布局或 wave 宽度，不是 swizzle
（swizzle 错只会让带 XOR 的那两行 FAIL）。

### 已经验了什么

没有真机、也没有本地 C 编译器，所以验的是**那套下标算术**：把 kernel 里的宏逐条
镜像一份，跑三个配置 ——

| 配置 | 结果 |
|---|---|
| C500 基线 K=16，128×128×256 | 15 条假设墙全过；原始 16 拍 / XOR 8 拍（下限 8）；布局往返、全局足迹、k 覆盖全过 |
| C600 默认 K=32，128×128×256 | 同上，读:MMA 变 1:4 |
| C600 大 tile K=32，256×128×128，8 wave | 同上；LDS 49152 B，acc 仍 64 个 VGPR |

同样的检查就是 `./mma_swizzle_c600 banks`，上机不用重写。这一步抓出了两个真错：
片段宽度是 `K/4` 不是 `K/8`（断言墙会直接挡住），以及 `-DMX_FRAG64_AS_V2I32`
那条备选路径原本写成了「向量的向量」，clang 不允许。

**没验的**：这份源码一行都没经过编译器，更没上过任何卡。

## 验证状态

`mma_teach_256.cu` 在 C500（xcore1000，MACA 3.3.0）上跑过：
256³ 对 CPU 参考 **PASS，0 / 65536 不符**；闭式归属公式与 `prov_256` 的 dump 逐元素一致；
教程第 05 节的 LDS 读图、`C[164][81]` 与 `C[5][3]` 的逐条部分和都是 `reads_256` / `partial_256`
的真机输出，不是推导值。

`tutorial_i8_256*` 三版之间的吞吐对比不在此分支给结论。

`mma_swizzle_256.cu` 也在同一台机器上跑过了，四个组合对照（4096³）：

| 组合 | us | TOPS | 相对基准 | 1024³ 正确性 |
|---|---|---|---|---|
| 同步搬运 + 原始布局（基准） | 1649.0 | 83.3 | 1.000× | PASS 0/1048576 |
| 异步搬运 + 原始布局 | 1631.4 | 84.2 | 1.011× | PASS 0/1048576 |
| 同步搬运 + XOR 布局 | 904.2 | 152.0 | **1.824×** | PASS 0/1048576 |
| **异步搬运 + XOR 布局** | **893.6** | **153.8** | **1.845×** | PASS 0/1048576 |

`bench` 把每个组合**各跑两轮、第二轮顺序整个颠倒**，差值小于 0.2%，
所以这不是时钟爬坡造成的假象。

两点值得单独记下来：

1. **异或必须提到全局侧做。** BSM 异步搬运要求 LDS 落点按线程号连续
   （基线那句代进去就是 `smem_A + tid*16`），所以「把第 j 块写到槽位 j^u」做不到。
   好在异或是对合的，「让槽位 s 去取第 s^u 块」是同一个布局，改源地址即可，
   读侧一个字不用动。全局侧 16 条 lane 取的仍是那 256 个连续字节，
   只换了取数的人，合并访问的足迹没变。
2. **异步搬运单独上只值 1.1%**，别误读成「异步没用」。这里单缓冲、发完立刻
   `arrive_gvmcnt(0)`，发出去和等回来之间什么都没有，没有可重叠的对象。
   要兑现它得双缓冲，而双缓冲要再来一份 64KB 的 LDS tile —— 放不下
   （和否掉 padding 的是同一堵墙）。接好异步通路是为后面上流水线留的接口。

证据分级：

| 结论 | 凭什么 | 状态 |
|---|---|---|
| 读指令 16 拍 → 8 拍，写指令仍在下限 | 地址公式的确定性推论，`banks` 穷举全部下标组合 | **已验** |
| swizzle 是双射（128 行 × 16 块，无越界无重叠） | 同上 | **已验** |
| 额外 LDS = 0 字节 | 行内重排，行距不变 | **已验** |
| 异或挪到全局侧后布局不变 | `banks` 的往返自检：写进去的块 ↔ 读出来的块全部对上 | **已验** |
| 全局侧合并访问足迹没变 | `banks` 的足迹自检：同一行 16 条 lane 仍取那 256 个连续字节 | **已验** |
| 数值正确性 | C500 实跑 256³ / 1024³，**四个组合**都 PASS | **已验** |
| 端到端 1.845×（异步+XOR） | C500 实跑 4096³，每组合两轮、第二轮顺序颠倒 | **已验** |
| 异步单独只值 1.1% | 同上实测；原因从代码形状直接读出（单缓冲、发完立刻 arrive） | **已验** |
| 「原本约九成时间耗在 LDS 读上」 | 由实测加速比与 2.00× 理论上限**反推**，非 profiler 读数 | 推论 |

### mma_pipeline_256.cu —— 搬运/计算重叠（本分支最快）

4096³，五个组合同源对照：

| 组合 | LDS/block | 驻留 block/CU | us | TOPS | 相对 |
|---|---|---|---|---|---|
| TK=256 顶部发射（= 上一步的终点） | 64 KB | 1 | 893 | 153.5 | 1.00× |
| TK=256 单缓冲晚发射 | 64 KB | 1 | 743 | 185.0 | 1.20× |
| TK=128 顶部发射 | 32 KB | **2** | 584 | 235.3 | 1.53× |
| **TK=128 单缓冲晚发射** | 32 KB | **2** | **427–515** | **267–322** | **1.73–2.09×** |
| TK=128 **双缓冲** | 64 KB | 1 | 733 | 187.6 | 1.22× |

**双缓冲比单缓冲晚发射最差的那次还慢 1.42 倍。** 原因不是流水线写错了，
是它要的第二份 LDS 把驻留 block 从 2 个压到 1 个 ——
驻留 1 个 block 的三行是 153.5 / 185.0 / 187.6 TOPS，驻留 2 个的两行是 235.3 / 267–322。
**占用率这条线比流水线那条线陡得多。** 两个 block 之间的重叠是硬件白送的，
覆盖面还比双缓冲买到的 block 内重叠更宽。

一处要说清的不稳定：`TK=128 单缓冲晚发射` 跨进程在 426.7‥514.7 us 之间跳（极差 20.6%，
7 次独立进程），其余四个组合极差都 < 2.2%。每次进程内两轮自洽（< 0.3%），
所以不是测量噪声，成因没有定位。但**即使每次都落在最差的 514.7，名次也不变**，
所以表里给区间而不是最好成绩。

| 结论 | 凭什么 | 状态 |
|---|---|---|
| 五个组合数值都对 | C500 实跑 256³ / 1024³，0 不符 | **已验** |
| 驻留 block/CU = 1 / 2 / 1 | `mcOccupancyMaxActiveBlocksPerMultiprocessor` 实测 | **已验** |
| 双缓冲比单缓冲晚发射慢 | C500 实跑 4096³，733 us vs 最差 515 us | **已验** |
